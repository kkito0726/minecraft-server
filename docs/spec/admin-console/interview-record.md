# admin-console ヒアリング記録

**作成日**: 2026-09-09
**ヒアリング実施**: 要件定義フェーズ（計画立案時 4 問 + 要件定義時 3 問）

## ヒアリング目的

本プロジェクトには PRD も既存の設計文書も存在せず、参照できるのは
`README.md` / `docs/backup-restore.md` / `docs/raspberry-pi.md` / `compose.yaml` / `.env.example` の
5 つの既存資料のみだった。これらは**サーバーの運用手順**を記述したものであり、
**管理コンソールをどう作るか**についての情報はゼロである。

そのため、以下の 2 段階でヒアリングを実施した。

1. **計画立案時（4 問）**: 設計の骨格を決める分岐 — 実行形態・認証・スコープ・要件定義の形式
2. **要件定義時（3 問）**: 要件の粒度を決める分岐 — 作業規模・既定の取得方式・オフサイト退避の扱い

加えて、ヒアリングでは解けない事実については**一次資料の直接確認**で埋めた（後述の「ヒアリング以外で解消した不確実性」）。

## 質問と回答

### Q1: Go バックエンドはどこで動かすか

**カテゴリ**: 未定義部分の詳細化
**背景**: バックエンドは `docker compose` の操作とバインドマウント `data/` への直接アクセスの両方が必要になる。
実行場所によってパスの解決方法とセキュリティ上の性質が根本的に変わるため、他のどの設計判断よりも先に決める必要があった。
特に「コンテナ内から `docker compose` を叩く」場合、`./data` がホスト基準で解決されるためパス変換が必要になり、
`/var/run/docker.sock` のマウントは実質的に root 権限の付与に等しい。

**選択肢**: ① Pi 上に systemd 常駐（推奨） ② compose にコンテナ追加 ③ Mac でローカル開発のみ

**回答**: **① Pi 上に systemd 常駐**

**信頼性への影響**:
- REQ-414（単一の静的バイナリ / linux/arm64 / 埋め込み配信）が 🔴 → 🔵
- REQ-411（`docker compose` にプロジェクトディレクトリ・プロジェクト名を明示）の必要性が確定（systemd 配下では作業ディレクトリがリポジトリと一致しないため）
- NFR-102（待ち受けアドレスの既定値）が新たに論点として浮上 — 後述の設計上の修正につながった
- `HOST_REPO_PATH` によるパス変換要件、および docker socket のマウントに関する要件が**不要になった**（設計の単純化）

### Q2: 管理画面の認証をどうするか

**カテゴリ**: 未定義部分の詳細化
**背景**: `docs/raspberry-pi.md` は「tailnet に招いた全員が 25565 に到達できる」ため
`MC_WHITELIST` を別レイヤーの制御として設けている、と明記している。
管理画面はワールドの削除まで可能であり、25565 より明確に危険度が高い。
にもかかわらず「Tailscale で守られているから」で無認証にすると、この既存の設計思想と矛盾する。

**選択肢**: ① 共有トークン（推奨） ② Tailscale 依存・アプリ側は無認証 ③ Tailscale Identity ヘッダ

**回答**: **① 共有トークン**

**信頼性への影響**:
- REQ-021（Bearer トークンの要求）が 🔴 → 🔵
- NFR-101（Tailscale + トークンの二段構え）が 🔴 → 🔵
- REQ-406（定数時間比較）、REQ-407（ストリーム RPC にも認証）、REQ-408（トークン長の fail-fast）、NFR-103（CSP）が
  トークン方式の帰結として派生（いずれも 🟡 — 一般的なセキュリティ対策としての推測）
- `tailscale serve` の設定に関する要件が不要になった

---

### Q3: v1 に入れる機能はどれか

**カテゴリ**: 優先順位・スコープ調整
**背景**: ユーザーの当初の依頼は「バックアップを取得したり、適応したり、複数ワールドデータを管理して入れ替える」であり、
サーバーの起動・停止・状態表示については言及がなかった。
しかし復元とワールド切替はいずれもサーバーの完全停止を必要とするため、
サーバー制御は依頼された 3 機能の**前提条件**として不可分である。この認識が正しいかを確認する必要があった。

**選択肢**（複数選択可）: ① バックアップ取得・一覧・削除 ② 復元 ③ 複数ワールド管理・切替 ④ サーバー起動/停止/状態表示

**回答**: **4 つすべて**

**信頼性への影響**:
- REQ-001〜REQ-016 の全機能要件が 🔴 → 🔵
- サーバー制御が独立した機能として v1 に含まれることが確定し、REQ-002 が「復元の副作用」ではなく独立要件になった
- 同時に、選択されなかった機能（コンソール UI、プレイヤー管理、TPS グラフ、`.env` 編集 UI）を
  **v2 として明示的に対象外とする**根拠が得られた

### Q4: 要件定義書の形式

**カテゴリ**: 進め方の確認
**背景**: ユーザーの依頼が「要件定義から始めましょう」であり、形式の指定がなかった。
リポジトリの既存 docs は散文形式だが、後続の TDD 実装（テストを先に書く）には
受け入れ基準が機械的に落ちている方が有利である。

**選択肢**: ① EARS 記法（tsumiki） ② docs/ に日本語の散文 ③ 両方

**回答**: **① EARS 記法（tsumiki）**

**信頼性への影響**:
- 要件が「システムは〜しなければならない」の形式に統一され、受け入れ基準への変換が機械的になった
- `docs/spec/admin-console/` 配下への出力（tsumiki の命名規則）が確定。
  当初計画していた `docs/requirements-admin-console.md` から変更

### Q5: 作業規模

**カテゴリ**: 進め方の確認
**背景**: 承認済みの実装計画がすでに proto スキーマ・内部インタフェース・フロー・テスト戦略まで
具体化されており、要件定義書が計画の焼き直しになる懸念があった。
一方で、後続の TDD 実装（フェーズ 5〜12）でテストを先に書く際、受け入れ基準が元ネタになる。

**選択肢**: ① フル機能開発（推奨） ② 軽量開発 ③ カスタム

**回答**: **① フル機能開発**

**信頼性への影響**:
- `user-stories.md` と `acceptance-criteria.md` を追加出力することが確定
- 非機能要件とエッジケースを網羅する方針が確定し、EDGE-001〜EDGE-106 が要件として明文化された
  （実装計画では「不確実性」の節に散在していたものが、検証可能な要件になった）

### Q6: バックアップの既定の取得方式

**カテゴリ**: 未定義部分の詳細化
**背景**: `docs/backup-restore.md` は HOT（稼働させたまま）と COLD（停止してから）の**両方**を記載しており、
COLD を「確実・推奨」と書いている。しかし画面にはどちらかを既定として置く必要があり、
どちらを既定にするかは docs からは決まらなかった。
なお Pi では再起動に数分かかるため、COLD を既定にすると気軽にバックアップを取れなくなる懸念があった。

**選択肢**: ① HOT を既定 ② COLD を既定

**回答**: **① HOT（稼働させたまま）を既定**

**信頼性への影響**:
- REQ-103〜REQ-107（`save-off` / `save-all` / `save-on` とその復旧）が**必須要件**として確定（🔵）。
  COLD 既定であればこれらは補助的な位置づけに留まっていた
- REQ-301（COLD）が「オプション要件」に降格（🔵 — docs に記載があるため出典は確実）
- `save-on` の保証（REQ-104）と無条件再送（REQ-105、REQ-106）の重要度が上がった。
  HOT が既定である以上、`save-off` が残るリスクは日常的に発生する

---

### Q7: バックアップのオフサイト退避を v1 に入れるか

**カテゴリ**: 追加要件の特定
**背景**: `docs/backup-restore.md` は「同じ Mac の中に置いているだけでは、ディスク障害で本体もろとも消える。
最低ひとつは別の場所にコピーが行くようにしておく」と明確に警告しており、`scp` の例まで示している。
この警告に対して管理コンソールが何も応えないのは、既存 docs の意図に反する可能性があった。

**選択肢**: ① v1 はローカルのみ（推奨） ② ダウンロードだけ v1 に入れる ③ 自動転送まで v1 に入れる

**回答**: **① v1 はローカルのみ**

**信頼性への影響**:
- REQ-418（他ホストへ転送しない）が 🔴 → 🔵
- 同時に **REQ-419 が新規要件として追加**（🔵）: 一覧画面において
  「バックアップがサーバーと同一のディスク上にしか存在しない」ことを常時明示する。
  これは選択肢 ① の説明文に含めた条件をユーザーが受け入れた形であり、
  docs の警告を機能として無視するのではなく、**利用者に可視化して手動退避を促す**という位置づけになった
- SSH 鍵の管理、転送失敗時のリトライ、転送先の設定管理に関する要件が v1 から除外された

## ヒアリング以外で解消した不確実性

ヒアリングでは答えの出ない事実については、一次資料の直接確認で埋めた。
これらは**推測ではなく実測**であるため、根拠として 🔵 を与えている。

| # | 不確実だった点 | 確認方法 | 結果 | 影響を受けた要件 |

| 1 | 複数ワールドを切り替える公式な手段があるか | itzg の公式ドキュメント（`docker-minecraft-server.readthedocs.io/en/latest/variables/`）を取得 | `LEVEL` 変数が存在。原文: "Maps to the level-name server property. You can either switch between world saves or run multiple containers with different saves by using the LEVEL option"（既定値 `world`） | REQ-012, REQ-117 |

## ヒアリング結果サマリー

### 確認できた事項

- **実行形態**: Pi 上に systemd 常駐する単一の静的バイナリ。コンテナ化せず、docker socket もマウントしない
- **認証**: Tailscale による到達制御 + `ADMIN_TOKEN` による認可の二段構え
- **v1 スコープ**: バックアップ（取得・一覧・削除・世代管理）、復元、複数ワールド管理・切替、サーバー制御の 4 機能すべて
- **既定の取得方式**: HOT。COLD は選択肢として提供
- **オフサイト退避**: v1 の対象外。ただし「ローカルにしか存在しない」ことの可視化は要件に含める
- **要件定義の形式**: EARS 記法、フル機能開発、日本語

### 追加/変更要件

| 種別 | 内容 | 契機 |
|---|---|---|
| 追加 | REQ-419（バックアップがローカルにしか存在しないことの常時明示） | Q7。オフサイトを対象外とした代償措置 |
| 追加 | NFR-102（待ち受けアドレスの既定値が Tailscale から到達可能であること） | Q1 の帰結。当初 `127.0.0.1:8787` を既定としていたが、Pi 上の systemd では別端末から開けないため `0.0.0.0:8787` に修正 |
| 追加 | REQ-108（`MC_SEED` を `compose up` の前に無条件クリア） | REQ-303 の設計中に発見。新規ワールド生成の完了待ちは最大 900 秒に及び、その間にプロセスが停止するとシードが `.env` に残留する |
| 昇格 | REQ-103〜REQ-107 が必須要件へ | Q6 で HOT を既定としたことにより、`save-off` の残留が日常的なリスクになった |
| 降格 | REQ-301（COLD）がオプション要件へ | Q6 |
| 除外 | オフサイト転送、SSH 鍵管理、転送リトライ | Q7 |
| 除外 | docker socket のマウント、ホスト/コンテナ間のパス変換 | Q1 |
| 除外 | `tailscale serve` の設定、Tailscale Identity ヘッダの解釈 | Q2 |

### 併せて修正することになった既存の不具合

要件定義の過程で、既存構成の不具合が 3 件見つかった。いずれも本要件の実装に含める。

1. `compose.yaml:78-79` と `README.md:181` が `MC_ENABLE_WHITELIST` を参照しているが、`.env` にも `.env.example` にも存在しない
2. `data/spigot.yml` は `docs/raspberry-pi.md` が手編集を指示しているのに、バックアップ集合に入っておらず `.env` からも再生成されない（→ REQ-004 に含めた）
3. `README.md:212` のバックアップレシピがファイル名に `MC_VERSION` を含まず、`docs/backup-restore.md` の主張と矛盾している（→ REQ-007 で統一）

### 残課題

| # | 内容 | 扱い |
|---|---|---|
| 1 | **`LEVEL` 指定時にワールドが `data/<名前>/` に作られるかは未検証。** itzg のドキュメントはディスク上の位置を明記していない | 実装フェーズ 2 を**ゲート**とし、実機で確認できるまで後続に進まない。失敗時のフォールバック（`data/worlds/<名前>/` に置き、アクティブなものを `data/world` へ移動）を用意済みで、変更範囲は `internal/world/switch.go` と `worldfs.Repository` の実装のみ |
| 2 | `rcon-cli list` の出力書式がサーバーのバージョンに依存する | EDGE-002 として「不明」表示にフォールバックする設計にした。機能の欠損は生じない |
| 3 | `MC_VERSION` の文字列と `DataVersion` の整数の対応表を持てない | 判定を「アーカイブ内のワールド」vs「現在ディスク上のワールド」の `DataVersion` 比較に限定した。`MC_VERSION` は表示と補助警告に留める |
| 4 | `docker compose ps --format json` の出力形状が Compose のバージョンに依存する | EDGE-003 として「必要なフィールドのみ解釈、未知フィールドは無視」の方針にした |
| 5 | NBT デコードライブラリの API 安定性が未確認 | 差し替え可能な境界（REQ-416）の背後に隔離。代替の自前実装で必要な型は 4 種のみ |
| 6 | `docs/raspberry-pi.md` 自体が「実機で未検証」と明記しており、現在の動作環境は開発者の Mac | Pi への移行は本要件の実装フェーズ 19 で扱う。要件は Pi を前提に書いてある |

### 信頼性レベル分布

**ヒアリング前**: 定量的な内訳は示さない。ヒアリング前には要件そのものが存在しておらず、
「もし既存 5 資料だけで書いていたら」という仮想の分布を数えることになるため、
精密な件数を示すと分かっていないことを分かっているように見せてしまう。

定性的に言えば、**赤信号が過半を占めていたはず**である。既存資料は**サーバーの運用手順**の記述であり、
実行形態・認証・スコープ・UI については情報がゼロだった。
唯一の例外がバックアップと復元の手順で、これは `docs/backup-restore.md` に検証済みの形で存在していた。

**ヒアリング後**（一次資料の直接確認を含む、実際の件数）:

| レベル | 件数 | 割合 |
|---|---|---|
| 🔵 青信号 | 36 | 42% |
| 🟡 黄信号 | 50 | 58% |
| 🔴 赤信号 | **0** | 0% |

**赤信号は 0 件。** 黄信号 50 件の大半は、
「既存の検証済み手順を自動化する際に必然的に生じる実装上の判断」
（排他制御、進捗の配信方式、パストラバーサル対策、境界値の扱いなど）であり、
元の手順の意図から逸脱する推測は含まれていない。
