# admin-console ユーザストーリー

**作成日**: 2026-09-09
**関連要件定義**: [requirements.md](requirements.md)
**ヒアリング記録**: [interview-record.md](interview-record.md)

**【信頼性レベル凡例】**
- 🔵 **青信号**: 既存 docs・実測値・ユーザーヒアリングを参考にした確実なストーリー
- 🟡 **黄信号**: 既存 docs・実測値・ヒアリングから妥当な推測によるストーリー
- 🔴 **赤信号**: 既存資料にない推測によるストーリー

## 登場人物

本システムの利用者は 1 名（サーバー管理者）のみである。
マルチユーザー・権限分掌は v1 の対象外（[interview-record.md](interview-record.md) Q2 参照）。

| 種別 | 説明 |
|---|---|
| **サーバー管理者** | Pi 5 と Minecraft サーバーを所有・運用する本人。tailnet の管理者でもある。ブラウザ（Mac）から Tailscale 経由で管理コンソールにアクセスする |
| **プレイヤー** | tailnet に招かれ、`MC_WHITELIST` に登録された参加者（最大 5 名）。**管理コンソールは使わない**が、サーバーの停止・ワールド切替の影響を受ける |

## エピック 1: バックアップを取る

### ストーリー 1.1: 稼働させたままバックアップを取る 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「稼働させたまま取る」節 + ヒアリング Q3・Q6 より*

**私は** サーバー管理者 **として**
**サーバーを止めずにワールドのバックアップを取りたい**
**そうすることで** プレイヤーを追い出すことなく、いつでも安全な復帰点を作れる

**関連要件**: REQ-004, REQ-007, REQ-103, REQ-104, REQ-409, NFR-001, NFR-002

**詳細シナリオ**:
1. 管理者がバックアップ画面を開き、「バックアップを取得」を押す
2. 取得方式として「稼働させたまま（HOT）」が既定で選択されている
3. 任意でメモ（例: 「バージョンを上げる前」）を入力して実行する
4. 進捗バナーに「保存を停止しています」→「ワールドを保存しています」→「アーカイブを作成しています」→「保存を再開しています」と順に表示される
5. 完了後、一覧の先頭に新しいバックアップが現れる
6. ファイル名は `backup-26.2-world-20260909-143000-before-upgrade.zip` の形式になっている

**前提条件**:
- サーバーが稼働している
- 他の操作が実行中でない

**制約事項**:
- 取得中はディスクへの書き込みが停止するため、その間のプレイヤーの行動は保存されない
- アーカイブに含まれるのは稼働中のワールド・`plugins`・`config`・`bukkit.yml`・`spigot.yml` のみ。サーバー jar とライブラリ（227MB）は再取得可能なので含まない
- `server.properties` は秘匿情報を含むため**含まない**

**優先度**: Must Have

### ストーリー 1.2: `save-on` の消し忘れを心配しないで済む 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「`save-on` を忘れると以降の変更がディスクに書かれない。スクリプトにするなら `trap` で必ず戻すこと」より*

**私は** サーバー管理者 **として**
**バックアップが途中で失敗しても、保存が自動的に再開されていてほしい**
**そうすることで** 「気づかないうちに数時間分のプレイが失われていた」という事故を避けられる

**関連要件**: REQ-104, REQ-105, REQ-106, REQ-107, REQ-202, REQ-203, EDGE-005

**詳細シナリオ**:
1. 管理者がバックアップを取得中に、ディスクが満杯になってアーカイブの作成が失敗する
2. システムは失敗を報告するが、**その前に保存を再開している**
3. 別の日、バックアップの取得中に Pi の電源が落ちる
4. Pi の再起動後、管理コンソールは起動と同時に無条件で保存の再開を試みる
5. その時点ではまだ Minecraft サーバーが起動していないため送信は失敗するが、システムはこれを異常としない
6. サーバーがヘルスチェックに合格した瞬間、システムは保存の再開を再送する
7. 画面上部に「中断された操作があります」という警告が表示され、管理者は状況を把握できる

**前提条件**: なし（これは常に成立していなければならない不変条件）

**制約事項**:
- RCON には「保存が有効かどうか」を問い合わせる手段がない。したがってシステムは状態を照会するのではなく、**冪等な `save-on` を無条件に再送する**という方針を採る
- 画面に表示される保存状態は推定値（「有効と推定」または「停止している可能性あり」）である

**優先度**: Must Have

**備考**: このストーリーは利用者が能動的に実行する操作ではなく、**システムが黙って守るべき不変条件**である。
受け入れ基準では、正常系ではなくエラー注入によって検証する。

### ストーリー 1.3: 古いバックアップが勝手に整理される 🔵

**信頼性**: 🔵 *ヒアリング Q3（v1 スコープに「世代管理」を含む）+ 現在バックアップが 0 件・保持機構が皆無であるという実測より*

**私は** サーバー管理者 **として**
**古いバックアップが自動的に消えてほしい**
**そうすることで** Pi の SSD を手動で見張らずに済む

**関連要件**: REQ-006, REQ-304, EDGE-103, EDGE-104

**詳細シナリオ**:
1. 管理者がバックアップ画面で保持世代数を 10 に設定する
2. 11 個目のバックアップを取得する
3. 取得の成功後、最も古い 1 個が自動的に削除される
4. 進捗ログに削除されたファイル名が記録される

**前提条件**: バックアップの取得が成功していること（失敗時には保持ポリシーを適用しない）

**制約事項**:
- 保持ポリシーの設定がどうであれ、**最も新しい 1 世代は必ず残る**。設定ミスによる全損の経路を塞ぐため
- 保持世代数に 0 以下は指定できない

**優先度**: Must Have

### ストーリー 1.4: バックアップがどこにあるかを見失わない 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「同じ Mac の中に置いているだけでは、ディスク障害で本体もろとも消える」+ ヒアリング Q7 より*

**私は** サーバー管理者 **として**
**バックアップがサーバーと同じディスクにしかないことを常に意識していたい**
**そうすることで** ディスク障害でワールドとバックアップを同時に失う事態を避けられる

**関連要件**: REQ-419, REQ-418

**詳細シナリオ**:
1. 管理者がバックアップ画面を開く
2. 一覧の上部に「これらのバックアップは Pi のディスク上にのみ存在します。別の場所への退避は手動で行ってください」という趣旨の表示が常にある
3. 表示には `docs/backup-restore.md` の手動退避手順（`scp`）への案内が添えられている

**前提条件**: なし

**制約事項**:
- v1 では自動転送もブラウザへのダウンロードも提供しない。**可視化のみ**
- この表示は条件付きではなく常時表示される（「一度読んだら消える」ようにはしない）

**優先度**: Must Have

**備考**: ヒアリング Q7 でオフサイト退避を v1 の対象外としたことの代償措置として追加されたストーリー。
docs の警告を機能として無視するのではなく、利用者に可視化して手動退避を促す位置づけ。

## エピック 2: バックアップから戻す

### ストーリー 2.1: 事故が起きたワールドを巻き戻す 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「復元手順」節 + ヒアリング Q3 より*

**私は** サーバー管理者 **として**
**バックアップの時点までワールドを巻き戻したい**
**そうすることで** 誤って地形を破壊したり、望まない変更をした後でもやり直せる

**関連要件**: REQ-008, REQ-009, REQ-113, REQ-114, REQ-115, REQ-116, REQ-123, NFR-203

**詳細シナリオ**:
1. 管理者がバックアップ一覧から対象を選び「復元」を押す
2. 事前確認の結果が表示される — バックアップのバージョン、現在のワールドのバージョン、両者の比較結果、ワールド名の一致状況
3. 管理者は現在のワールド名を完全一致で入力して確認する
4. 実行すると進捗が「復元内容を確認しています」→「空き容量を確認しています」→「サーバーを停止しています」→「現在のワールドを退避しています」→「アーカイブを展開しています」→「サーバーを起動しています」と進む
5. 完了後、ワールド画面の「退避したワールド」に `world.broken-20260909-143000` が現れる
6. 管理者はサーバーに接続して問題がないことを確認したうえで、退避を手動で削除する

**前提条件**:
- 復元対象のバックアップが存在する
- 展開後のサイズの 1.2 倍以上の空き容量がある

**制約事項**:
- **既存のワールドに上書き展開はしない。** 必ず退避してから展開する（上書きすると、バックアップに含まれない新しい region ファイルが残り、古い地形と新しい地形が同居した壊れたワールドになる）
- 退避は `rm` ではなく `mv`。失敗しても戻せる
- **退避は自動削除しない。** 管理者が動作を確認してから消す
- 復元の途中で中断する手段は提供しない（「退避済みかつ展開途中」という最も復旧困難な状態を作るため）

**優先度**: Must Have

### ストーリー 2.2: バージョンの食い違いに気づける 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「バージョンとの関係 — ワールドのアップグレードは片道」より*

**私は** サーバー管理者 **として**
**復元しようとしているバックアップが今のサーバーのバージョンと合っているかを、実行前に知りたい**
**そうすることで** 戻せないアップグレードを気づかずに走らせてしまうことを避けられる

**関連要件**: REQ-008, REQ-109, REQ-110, REQ-111, REQ-412, REQ-413, EDGE-001

**詳細シナリオ**:
1. 管理者が `MC_VERSION` を上げた後、古いバックアップを復元しようとする
2. 事前確認がバックアップ内の `level.dat` を読み、`DataVersion` が現在のワールドより小さいことを検出する
3. 画面に「このバックアップは現在のワールドより古いバージョンです。復元すると片道アップグレードが再度実行されます」と表示される
4. 「バージョンの警告を理解しました」のチェックボックスが現れ、これをチェックしない限り実行ボタンが押せない
5. 逆に、バックアップが現在より新しい場合は「現在の `MC_VERSION` では開けない可能性が高い」と警告される

**前提条件**: バックアップ内および現在のワールドの `level.dat` が読み取れること

**制約事項**:
- 判定に使うのは**ファイル名ではなくアーカイブ内の `level.dat`**。ファイル名は人間が改名できるため信用しない
- 判定に使うのは表示文字列（`"26.2"`）ではなく**整数の `DataVersion`（`4903`）**
- `MC_VERSION` の文字列と `DataVersion` の対応表は持たない。比較は「アーカイブ内のワールド」対「現在ディスク上のワールド」で行う
- `level.dat` が読めない場合はバージョンを「不明」として扱い、それでも一覧表示と復元自体は継続できる

**優先度**: Must Have

### ストーリー 2.3: 復元先のワールドを取り違えない 🟡

**信頼性**: 🟡 *複数ワールド対応により生じる新たな失敗経路からの妥当な推測*

**私は** サーバー管理者 **として**
**バックアップに入っているワールド名が今稼働中のものと違う場合に、それを教えてほしい**
**そうすることで** 「復元したのに何も変わらない」という状態に陥らずに済む

**関連要件**: REQ-112, REQ-113

**詳細シナリオ**:
1. 管理者が `world` のバックアップを取った後、`creative` というワールドに切り替えて遊んでいる
2. `world` のバックアップを復元しようとする
3. 事前確認が「バックアップのワールド名は `world`、現在稼働中は `creative`」という不一致を検出する
4. 画面に 2 つの選択肢が提示される:
   - **`world` として復元し、稼働ワールドも `world` に切り替える**（既定）
   - **`creative` として復元する**（展開時にパスを書き換える）
5. 管理者が意図を選んでから実行する

**前提条件**: 複数のワールドが存在し、稼働中のものが切り替えられている

**制約事項**:
- 何も考えずに展開すると `data/world` が戻るだけで、稼働中の `data/creative` は変化しない。
  利用者からは「復元ボタンを押したのに何も起きなかった」ように見える。この経路を塞ぐための選択である

**優先度**: Must Have

**備考**: このストーリーは単一ワールド時代には存在しなかった失敗経路である。
複数ワールド対応（エピック 3）を入れたことによって新たに生じたため、両者は同時に実装する必要がある。

## エピック 3: 複数のワールドを持ち替える

### ストーリー 3.1: 遊ぶワールドを切り替える 🔵

**信頼性**: 🔵 *ヒアリング Q3 + itzg ドキュメントの `LEVEL` 変数の記述より*

**私は** サーバー管理者 **として**
**サバイバル用とクリエイティブ用のワールドを持って、遊ぶ方を切り替えたい**
**そうすることで** 用途ごとにワールドを分けられ、片方の実験がもう片方に影響しない

**関連要件**: REQ-011, REQ-012, REQ-117, REQ-118, REQ-119, REQ-122, NFR-204

**詳細シナリオ**:
1. 管理者がワールド画面を開くと、`world`（稼働中）と `creative` が一覧に並んでいる
2. それぞれにサイズ・最終プレイ日時・`level.dat` から読んだバージョンが表示されている
3. `creative` の「切り替え」を押す
4. 確認ダイアログに「`world` は削除されません。いつでも戻せます」と明示される
5. 実行すると「ワールドを保存しています」→「サーバーを停止しています」→「設定を書き換えています」→「サーバーを起動しています」→「起動を確認しています」と進む
6. 完了後、稼働中のバッジが `creative` に移り、`world` はサイズもそのままに一覧に残っている

**前提条件**: 切り替え先のワールドが存在する（存在しない名前を指定した場合は新規生成として扱う）

**制約事項**:
- 切替には**サーバーの完全な停止と再作成が必要**。`docker compose restart` では反映されない
  （`OVERRIDE_SERVER_PROPERTIES=TRUE` により `server.properties` は起動時に `.env` から再生成され、サーバープロセスはそれを起動時に 1 回だけ読むため）
- 切替中はプレイヤーが接続できない
- **切替前のワールドのデータは 1 バイトも動かない**

**優先度**: Must Have

### ストーリー 3.2: 危ないことを試す前に複製しておく 🔵

**信頼性**: 🔵 *ヒアリング Q3（v1 スコープに「複数ワールド管理」を選択）より*

**私は** サーバー管理者 **として**
**今のワールドを別名でまるごと複製したい**
**そうすることで** 大規模な建築や地形改変を試す前に、安全な分岐点を作れる

**関連要件**: REQ-014, REQ-120, REQ-121, REQ-122, EDGE-006, EDGE-105

**詳細シナリオ**:
1. 管理者がワールド一覧で `world` の「複製」を押す
2. 複製先の名前として `world-experiment` を入力する
3. システムが空き容量（複製元のサイズの 1.1 倍）を事前に確認する
4. 稼働中のワールドなので、複製の前に保存を停止し、保存を実行してから複製する
5. 複製の完了後、保存が再開される
6. 一覧に `world-experiment` が現れる。**稼働中のワールドは変わらない**

**前提条件**: 複製先の名前が既存のワールドと重複していない

**制約事項**:
- 複製は切替を伴わない。切り替えたい場合は別途「切り替え」を実行する
- 複製元の `session.lock` は複製先に含めない（起動時に作り直されるため）
- 空き容量が不足している場合、**1 バイトもコピーせずに中止する**

**優先度**: Should Have

### ストーリー 3.3: まっさらなワールドで始める 🔵

**信頼性**: 🔵 *ヒアリング Q3 + `docs/backup-restore.md`「ワールドを作り直す」節より*

**私は** サーバー管理者 **として**
**新しいワールドを名前を付けて作りたい（できればシードを指定して）**
**そうすることで** 既存のワールドを消さずに新しく始められる

**関連要件**: REQ-013, REQ-108, REQ-303, EDGE-007, NFR-003

**詳細シナリオ**:
1. 管理者が「新しいワールドを作成」を押し、名前 `hardcore` と任意のシード値を入力する
2. システムが `.env` の `MC_SEED` にシードを書き、`MC_LEVEL` を `hardcore` にしてサーバーを再作成する
3. Paper がワールドを生成する。進捗は「サーバーを起動しています」のまま最大 900 秒待機する
4. 生成が完了すると `hardcore` が稼働中になる
5. **次回以降の起動でシードが意図せず効かないよう**、`MC_SEED` は `compose up` を伴うすべての操作の冒頭で空に戻される

**前提条件**: 名前が既存のワールドと重複していない

**制約事項**:
- ディレクトリはシステムが作らない。Paper に生成させる
- 既存ワールド（最大 300 秒）より長い待機時間（最大 900 秒）を許容する
- Pi ではワールド生成に相当な時間がかかる可能性がある

**優先度**: Should Have

### ストーリー 3.4: 使わなくなったワールドを片付ける 🟡

**信頼性**: 🟡 *ヒアリング Q3 に「削除」が含まれることは確実だが、退避方式を既定とする点は推測*

**私は** サーバー管理者 **として**
**使わなくなったワールドを消して容量を空けたい**
**そうすることで** 30MB 単位でディスクを消費する不要なワールドを整理できる

**関連要件**: REQ-015, REQ-016, REQ-123, REQ-124, REQ-305, EDGE-102, EDGE-105

**詳細シナリオ**:
1. 管理者が `world-experiment` の「削除」を押す
2. 確認ダイアログでワールド名 `world-experiment` を完全一致で入力する
3. 既定では即座に削除せず `data/world-experiment.deleted-20260909-143000` へ退避される
4. 「退避したワールド」の一覧に現れ、そこから完全に削除できる
5. 稼働中のワールドを削除しようとした場合は拒否され、「先に別のワールドへ切り替えてください」と案内される

**前提条件**: 削除対象が稼働中でないこと

**制約事項**:
- 稼働中のワールドは削除できない
- 名前の完全一致入力を要求する
- `logs` / `plugins` / `config` / `cache` / `libraries` / `versions` は予約名として、そもそもワールドとして扱われない

**優先度**: Should Have

### ストーリー 3.5: 退避されたディレクトリを片付ける 🟡

**信頼性**: 🟡 *`docs/backup-restore.md`「問題なく動くことを確認してから、退避した `data/world.broken-*` を削除する」を画面操作に落とした推測*

**私は** サーバー管理者 **として**
**復元や削除で退避されたディレクトリを一覧で見て、確認後に消したい**
**そうすることで** 退避が無自覚に溜まってディスクを圧迫することを防げる

**関連要件**: REQ-010, REQ-305, EDGE-005

**詳細シナリオ**:
1. 管理者がワールド画面の「退避したワールド」セクションを開く
2. `world.broken-20260909-143000`（元のワールド名・退避日時・サイズ付き）が並んでいる
3. 復元後のサーバーが正常に動くことを確認したうえで、「完全に削除」を押す
4. 確認後、ディレクトリが削除される

**前提条件**: 退避されたディレクトリが存在する

**制約事項**:
- システムはこれを自動削除しない（`docs/backup-restore.md` の手順を尊重）
- 任意で日数による自動削除を設定できる（既定は無効）

**優先度**: Should Have

## エピック 4: サーバーの様子を見て、動かす

### ストーリー 4.1: サーバーの状態をひと目で把握する 🔵

**信頼性**: 🔵 *ヒアリング Q3（v1 スコープに「サーバー起動/停止/状態表示」を選択）+ `README.md` の状態確認手順より*

**私は** サーバー管理者 **として**
**サーバーが動いているか、どのワールドで動いているかを一画面で知りたい**
**そうすることで** ターミナルを開いて `docker compose ps` を打たずに済む

**関連要件**: REQ-001, REQ-203, EDGE-002, EDGE-003

**詳細シナリオ**:
1. 管理者がトップ画面を開く
2. コンテナの状態（実行中 / 停止 / 再起動中 / 不在）とヘルスチェックの結果が表示される
3. 稼働中のワールド名、その `level.dat` から読んだバージョン、`.env` の `MC_VERSION` が並ぶ
4. オンライン人数と最大人数、コンテナの起動時刻が表示される
5. 保存が停止している可能性がある場合は警告が出る
6. 中断された操作が検出されている場合は赤い帯が表示される

**前提条件**: なし（サーバーが停止していても状態画面は表示される）

**制約事項**:
- オンライン人数の取得に失敗した場合は「不明」と表示し、画面全体を失敗させない
- 保存状態は推定値であって、サーバーに問い合わせた実測値ではない

**優先度**: Must Have

---

### ストーリー 4.2: サーバーを止めて、また動かす 🔵

**信頼性**: 🔵 *ヒアリング Q3 より*

**私は** サーバー管理者 **として**
**サーバーを画面から止めたり動かしたりしたい**
**そうすることで** Pi に SSH で入らずにメンテナンスができる

**関連要件**: REQ-002, REQ-411, NFR-003

**詳細シナリオ**:
1. 管理者がトップ画面の「停止」を押す
2. 進捗が「サーバーを停止しています」と表示され、最大 90 秒待機する（`stop_grace_period` の 60 秒を尊重するため）
3. 完了後、状態が「停止」に変わる
4. 「起動」を押すと `docker compose up -d` が実行され、起動完了（最大 300 秒）まで待機する

**前提条件**: 他の操作が実行中でない

**制約事項**:
- 停止は `stop_grace_period: 60s` を尊重する。10 秒の既定値で強制終了すると保存の途中でチャンクが壊れる
- 起動完了の判定はログの `Done (` の検出とヘルスチェックの合格の**いずれか**で行う

**優先度**: Must Have

## エピック 5: 安心して操作する（横断的関心事）

### ストーリー 5.1: 画面を閉じても操作が続く 🟡

**信頼性**: 🟡 *`stop_grace_period: 60s` と Paper の起動時間から、操作がリロードを跨ぐという推測*

**私は** サーバー管理者 **として**
**復元の途中で画面を再読み込みしても、進捗が最初から見えていてほしい**
**そうすることで** 「今どうなっているか分からない」まま待たされずに済む

**関連要件**: REQ-017, REQ-018, REQ-019, REQ-020, REQ-127, REQ-128, NFR-202, EDGE-106

**詳細シナリオ**:
1. 管理者が復元を開始する。進捗バナーにステップとログが流れる
2. 途中でブラウザを再読み込みする
3. 画面が復帰すると、**再読み込み前のログ行がすべて残った状態で**バナーが再表示される
4. 別の端末（スマートフォン）から同じ URL を開いても、進行中の操作が見える
5. ネットワークが一時的に切れた場合、最後に受信した位置の次から自動的に購読を再開する

**前提条件**: 操作が進行中であること

**制約事項**:
- 進捗は React の状態としてではなく、サーバー側のリソースとして管理される。画面が持つのは「今どの操作を見ているか」だけ
- 進捗イベントには保持上限があり、超過分は古いものから破棄されるが、**最新の状態は必ず復元できる**

**優先度**: Must Have

---

### ストーリー 5.2: 危ない同時操作を防いでもらう 🟡

**信頼性**: 🟡 *バックアップ・復元・切替・起動停止がすべて `data/` を変更するという事実からの推測*

**私は** サーバー管理者 **として**
**うっかり 2 つの操作を同時に走らせてしまわないようにしてほしい**
**そうすることで** ワールドデータが壊れる事故を防げる

**関連要件**: REQ-101, REQ-102, REQ-201

**詳細シナリオ**:
1. 管理者がバックアップの取得を開始する
2. 進行中、ワールド画面へ移動する
3. 「切り替え」「複製」「削除」などの変更を伴うボタンがすべて押せない状態になっている
4. 画面上部のバナーが「バックアップを取得しています」と実行中の操作を示している
5. 仮に別のタブから API を直接呼んだとしても、サーバー側が拒否する

**前提条件**: なし

**制約事項**:
- 排他はサーバー側で担保される。画面の無効化はその反映にすぎない
- 排他はプロセス内のロックとファイルロックの二段構えで、バックエンドの再起動を跨いでも中断を検出できる

**優先度**: Must Have

---

### ストーリー 5.3: 自分以外が管理画面を開けない 🔵

**信頼性**: 🔵 *ヒアリング Q2 + `docs/raspberry-pi.md`「tailnet に招いた全員が到達できる」という既存の認識より*

**私は** サーバー管理者 **として**
**tailnet に招いたプレイヤーが管理画面を操作できないようにしたい**
**そうすることで** 遊びに招いた相手が誤って（あるいは故意に）ワールドを消せない

**関連要件**: REQ-021, REQ-406, REQ-407, REQ-408, NFR-101, NFR-102, NFR-103

**詳細シナリオ**:
1. プレイヤーが tailnet 内から管理コンソールの URL を開く
2. トークンの入力を求められ、値を知らないため先に進めない
3. 管理者自身は初回にトークンを入力し、以後はブラウザに保持される
4. トークンが無効になった場合、システムは保持された値を破棄して再入力を求める

**前提条件**: `.env` に 32 文字以上の `ADMIN_TOKEN` が設定されている

**制約事項**:
- Tailscale は**到達の制御**であって認可ではない。tailnet 参加者は全員 URL に到達できる
- トークンが 32 文字未満の場合、バックエンドは起動時に異常終了し、生成コマンドを案内する
- 進捗のストリーミング RPC にも同じ認証が適用される

**優先度**: Must Have
