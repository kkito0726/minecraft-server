# admin-console 受け入れ基準

**作成日**: 2026-09-09
**関連要件定義**: [requirements.md](requirements.md)
**関連ユーザストーリー**: [user-stories.md](user-stories.md)

**【信頼性レベル凡例】**
- 🔵 **青信号**: 既存 docs・実測値・ヒアリングを参考にした確実な基準
- 🟡 **黄信号**: 既存 docs・実測値・ヒアリングから妥当な推測による基準
- 🔴 **赤信号**: 既存資料にない推測による基準

## この文書の使い方

各テストケースは実装フェーズの **TDD における RED フェーズの元ネタ**である。
テストを先に書き（失敗を確認し）、実装で通す。

テスト種別の記号:

| 記号 | 種別 | 実行方法 |
|---|---|---|
| **U** | ユニットテスト | `go test ./...` / `vitest`。外部依存なし |
| **I** | 統合テスト | `go test -tags=integration ./...`。実ファイルシステム + `docker` のスタブ実行ファイル |
| **E** | E2E テスト | `playwright test`。実バイナリ + `fake-docker.sh` + 一時プロジェクトディレクトリ |
| **L** | 静的検査 | リンタ・コードレビュー。入力と期待出力を持つテストではないため、CI の別ジョブとして扱う |
| **M** | 手動確認 | 実機（Pi または Mac の Docker）でのみ検証可能 |

**L と M は TDD の RED フェーズの対象外**である。L は実装後に CI が恒常的に検査し、M は実機でのみ確認する。
TDD で先に書くのは U / I / E の 3 種のみ。

## REQ-004 / REQ-103 / REQ-104: 稼働させたままのバックアップ取得 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「稼働させたまま取る」節（一往復の検証済み手順）より*
**関連ストーリー**: [1.1](user-stories.md#ストーリー-11-稼働させたままバックアップを取る), [1.2](user-stories.md#ストーリー-12-save-on-の消し忘れを心配しないで済む)

### Given（前提条件）
- サーバーが稼働しており、ヘルスチェックに合格している
- 他の操作が実行中でない
- `.env` の `MC_LEVEL` が `world`、`MC_VERSION` が `26.2`

### When（実行条件）
- 取得方式 HOT でバックアップの取得を要求する

### Then（期待結果）
- RCON の呼び出しが `save-off` → `save-all` → （アーカイブ作成）→ `save-on` の順で発生する
- `backups/` に `backup-26.2-world-<日時>.zip` が作成される
- アーカイブに `data/world/`・`data/plugins/`・`data/config/`・`data/bukkit.yml`・`data/spigot.yml` が含まれる
- アーカイブに `data/server.properties` が**含まれない**
- 操作が成功として完了する

### テストケース

#### 正常系

- [ ] **TC-004-01**: HOT バックアップの呼び出し順序 **U** 🔵
  - **入力**: HOT モードでの取得要求。`fakercon` と `fakecompose` が呼び出しを記録する
  - **期待結果**: 記録された呼び出し列が `[SaveOff, SaveAll, ..., SaveOn]` の順である
  - **信頼性**: 🔵 *`docs/backup-restore.md` の手順そのもの*

- [ ] **TC-004-02**: アーカイブの構成が網羅列挙と完全一致する **I** 🔵
  - **入力**: `data/` 配下に対象 5 項目と非対象（`server.properties`・`libraries/`・`versions/`・`cache/`・`logs/`・`*.jar`・`ops.json`・`whitelist.json`）の双方を配置した一時ディレクトリでの取得要求
  - **期待結果**: 生成された zip のエントリの**ルート集合が `{data/world/, data/plugins/, data/config/, data/bukkit.yml, data/spigot.yml}` と集合として完全一致する**。「非対象が含まれないこと」を個別に確認するのではなく、集合の一致で検証する（REQ-004 の網羅列挙）
  - **信頼性**: 🔵 *`docs/backup-restore.md`「何をバックアップすればいいか」の表 + `spigot.yml`/`bukkit.yml` の欠落修正*
  - **備考**: 対象を包含リストで実装すると「非対象が入らない」は自明に成立し、独立した性質として検証できない。集合の完全一致で検証することで、**将来 `data/` に新しいパスが増えたときに意図せず混入する**経路を捕捉できる

- [ ] **TC-004-03**: ファイル名の形式 **U** 🔵
  - **入力**: `MC_VERSION=26.2`、`MC_LEVEL=world`、メモなし
  - **期待結果**: `backup-26.2-world-20260909-143000.zip` の形式に一致する
  - **信頼性**: 🔵 *`docs/backup-restore.md`「バックアップのファイル名にバージョンを入れておく」*

- [ ] **TC-004-04**: メモ付きのファイル名 **U** 🟡
  - **入力**: メモ `before upgrade`
  - **期待結果**: 空白と記号が除去され `backup-26.2-world-20260909-143000-before-upgrade.zip` になる
  - **信頼性**: 🟡 *REQ-302（オプション要件）からの推測*

- [ ] **TC-004-05**: 対象ワールドが `MC_LEVEL` に従う **I** 🟡
  - **入力**: `.env` の `MC_LEVEL=creative`、`data/creative/` と `data/world/` の双方が存在
  - **期待結果**: アーカイブに `data/creative/` が含まれ、`data/world/` が**含まれない**。ファイル名にも `creative` が入る
  - **信頼性**: 🟡 *REQ-409（`world` を固定値として扱わない）からの推測。既存手順は `data/world` を固定値にしている*

- [ ] **TC-004-06**: COLD バックアップの呼び出し順序 **U** 🔵
  - **入力**: COLD モードでの取得要求
  - **期待結果**: 呼び出し列が `[Down, ..., Up, WaitReady]` であり、`SaveOff`/`SaveOn` を含まない
  - **信頼性**: 🔵 *`docs/backup-restore.md`「停止してから取る」節*

- [ ] **TC-004-07**: 保管先ディレクトリの自動作成 **I** 🟡
  - **入力**: `backups/` が存在しない状態での取得要求
  - **期待結果**: ディレクトリが作成され、取得が成功する
  - **信頼性**: 🟡 *EDGE-008 からの推測*

#### 異常系

- [ ] **TC-004-E01**: アーカイブ作成の失敗時にも保存が再開される **U** 🔵
  - **入力**: `archive.Create` がエラーを返すよう注入した状態での HOT 取得要求
  - **期待結果**: 操作は失敗として記録されるが、**`SaveOn` が呼ばれている**。呼び出し列は `[SaveOff, SaveAll, SaveOn]`
  - **信頼性**: 🔵 *`docs/backup-restore.md`「`save-on` を忘れると以降の変更がディスクに書かれない。`trap` で必ず戻すこと」*

- [ ] **TC-004-E02**: 未完成のアーカイブが一覧に現れない **I** 🟡
  - **入力**: 書き込みの途中で失敗する取得要求
  - **期待結果**: `.part` の拡張子を持つ一時ファイルは一覧に現れず、正常終了時にのみ名前が変更される
  - **信頼性**: 🟡 *中断されたアーカイブを有効なバックアップとして表示しないための推測*

- [ ] **TC-004-E03**: サーバー停止中の HOT 取得 **U** 🟡
  - **入力**: コンテナが停止している状態での HOT 取得要求
  - **期待結果**: RCON の呼び出しを省略し、アーカイブの作成のみを行って成功する
  - **信頼性**: 🟡 *REQ-202 からの推測*

## REQ-105 / REQ-106 / REQ-107: 保存の再開の復旧 🔵

**信頼性**: 🔵 *`docs/backup-restore.md` の警告より。ただし「無条件再送」という手法は 🟡*
**関連ストーリー**: [1.2](user-stories.md#ストーリー-12-save-on-の消し忘れを心配しないで済む)

### Given（前提条件）
- 前回の実行がバックアップの途中で異常終了し、ロックファイルに「保存を停止した」記録が残っている

### When（実行条件）
- バックエンドのプロセスが起動する

### Then（期待結果）
- 無条件に `save-on` が送信される
- コンテナが停止していて送信が失敗しても、プロセスは異常終了しない
- コンテナがヘルスチェック不合格から合格へ遷移した時点で `save-on` が再送される
- 状態情報の「中断された操作を検出」が真になり、ロックファイルが削除される

### テストケース

#### 正常系

- [ ] **TC-105-01**: 起動時の無条件 `save-on` **U** 🟡
  - **入力**: ロックファイルの有無にかかわらずバックエンドを起動
  - **期待結果**: `fakercon` に `SaveOn` が 1 回記録される
  - **信頼性**: 🟡 *RCON に保存状態の照会手段がないため、冪等な再送を選んだという推測*

- [ ] **TC-105-02**: コンテナ停止中の送信失敗を異常としない **U** 🟡
  - **入力**: `fakercon` がエラーを返す状態で起動
  - **期待結果**: 起動が成功し、エラーはログにのみ記録される
  - **信頼性**: 🟡 *起動順序に依存しないための推測*

- [ ] **TC-105-03**: healthy 遷移での再送 **U** 🟡
  - **入力**: `fakecompose` の状態を「不合格」→「不合格」→「合格」の順に返すよう設定
  - **期待結果**: 遷移が起きた 1 回だけ `SaveOn` が追加送信される（合格が続く間は再送しない）
  - **信頼性**: 🟡 *REQ-106 からの推測*

- [ ] **TC-105-04**: 中断の検出 **U** 🟡
  - **入力**: 存在しないプロセス ID を持つロックファイルを配置して起動
  - **期待結果**: 状態情報の「中断された操作を検出」が真になり、ロックファイルが削除される
  - **信頼性**: 🟡 *REQ-107 からの推測*

- [ ] **TC-105-05**: 生存中のプロセスのロックは削除しない **U** 🟡
  - **入力**: 自身のプロセス ID を持つロックファイル
  - **期待結果**: ロックファイルが削除されない
  - **信頼性**: 🟡 *多重起動時の誤削除を防ぐための推測*

- [ ] **TC-105-06**: 中断警告の表示 **E** 🟡
  - **入力**: 中断された操作が検出されている状態で画面を開く
  - **期待結果**: 画面上部に警告が表示され続ける（REQ-203）
  - **信頼性**: 🟡 *REQ-203 からの推測*

## REQ-006: 保持ポリシーの適用 🔵

**信頼性**: 🔵 *ヒアリング Q3 で「世代管理」が v1 スコープに含まれることを確認*
**関連ストーリー**: [1.3](user-stories.md#ストーリー-13-古いバックアップが勝手に整理される)

### Given（前提条件）
- 保持世代数が 10 に設定され、既に 10 件のバックアップが存在する

### When（実行条件）
- 11 件目のバックアップの取得が成功する

### Then（期待結果）
- 最も古い 1 件が削除され、10 件が残る
- 削除されたファイル名が操作ログに記録される

### テストケース

#### 正常系

- [ ] **TC-006-01**: 世代数による削除 **U** 🔵
  - **入力**: 保持世代数 10、既存 10 件、新規 1 件
  - **期待結果**: 作成日時が最も古い 1 件が削除され、合計 10 件になる
  - **信頼性**: 🔵 *ヒアリングで確定した機能*

- [ ] **TC-006-02**: 日数による削除 **U** 🟡
  - **入力**: 保持日数 7、7 日より古いものが 3 件
  - **期待結果**: 3 件が削除される
  - **信頼性**: 🟡 *REQ-304（オプション要件）からの推測*

- [ ] **TC-006-03**: 両方の条件を満たすものだけ削除 **U** 🟡
  - **入力**: 保持世代数 10 かつ保持日数 7。世代数では残るが日数では消える件、およびその逆が混在
  - **期待結果**: 両方の条件で削除対象になったものだけが削除される

- [ ] **TC-006-04**: 取得の失敗時には適用しない **U** 🟡
  - **入力**: アーカイブ作成が失敗した取得要求
  - **期待結果**: 保持ポリシーが適用されず、既存のバックアップが 1 件も削除されない
  - **信頼性**: 🟡 *「取得の成功直後に適用」という REQ-006 の文言からの推測*

#### 境界値

- [ ] **TC-006-B01**: 最低 1 世代の保証 **U** 🟡
  - **入力**: 保持日数 1、すべてのバックアップが 1 年前
  - **期待結果**: 最も新しい 1 件が残り、削除されない
  - **信頼性**: 🟡 *EDGE-103。設定ミスによる全損を防ぐための推測*

- [ ] **TC-006-B02**: 保持世代数の下限 **U** 🟡
  - **入力**: 保持世代数 0 および -1
  - **期待結果**: いずれも拒否される
  - **信頼性**: 🟡 *EDGE-104 からの推測*

- [ ] **TC-006-B03**: バックアップ 0 件での適用 **U** 🟡
  - **入力**: バックアップが 1 件も存在しない状態
  - **期待結果**: エラーにならず、何も削除しない
  - **信頼性**: 🟡 *EDGE-104 の周辺ケース*

## REQ-008 / REQ-109〜REQ-113: 復元の事前確認 🔵

**信頼性**: 🔵 *`docs/backup-restore.md`「バージョンとの関係」節より*
**関連ストーリー**: [2.2](user-stories.md#ストーリー-22-バージョンの食い違いに気づける), [2.3](user-stories.md#ストーリー-23-復元先のワールドを取り違えない)

### Given（前提条件）
- 復元対象のバックアップと現在のワールドが存在する

### When（実行条件）
- 事前確認を要求する

### Then（期待結果）
- アーカイブ内の `level.dat` と現在のワールドの `level.dat` から `DataVersion` を取得し、比較結果を返す
- ワールド名の一致状況を返す
- **副作用が一切発生しない**（ファイルの作成・変更・削除、コンテナの操作をしない）

### テストケース

#### 正常系（バージョン判定の全組み合わせ）

- [ ] **TC-008-01**: 一致 **U** 🔵
  - **入力**: アーカイブ `DataVersion=4903`、現在 `4903`
  - **期待結果**: 判定が「一致」、承諾の要求なし
  - **信頼性**: 🔵 *`level.dat` の実測値に基づく*

- [ ] **TC-008-02**: アーカイブの方が古い **U** 🔵
  - **入力**: アーカイブ `4820`、現在 `4903`
  - **期待結果**: 判定が「古い / アップグレードが走る」、警告文に「片道アップグレードが再度実行される」旨を含む、承諾が必要
  - **信頼性**: 🔵 *`docs/backup-restore.md`「`MC_VERSION` を上げた後に古いバックアップを復元すると、再び同じアップグレードが走る」*

- [ ] **TC-008-03**: アーカイブの方が新しい **U** 🔵
  - **入力**: アーカイブ `4950`、現在 `4903`
  - **期待結果**: 判定が「新しい / 非互換」、警告文に「現在の `MC_VERSION` では開けない可能性が高い」旨を含む、承諾が必要
  - **信頼性**: 🔵 *`docs/backup-restore.md`「新しいバージョンで保存されたワールドを古い `MC_VERSION` に戻すことはできない」*

- [ ] **TC-008-04**: 判定不能 **U** 🟡
  - **入力**: アーカイブの `level.dat` が読めない
  - **期待結果**: 判定が「不明」、承諾が必要
  - **信頼性**: 🟡 *EDGE-001。読めない場合を安全側（承諾必須）に倒すという推測*

- [ ] **TC-008-05**: ワールド名の一致 **U** 🟡
  - **入力**: アーカイブのワールド名 `world`、稼働中 `world`
  - **期待結果**: 名前の不一致が偽
  - **信頼性**: 🟡 *REQ-112 からの推測*

- [ ] **TC-008-06**: ワールド名の不一致 **U** 🟡
  - **入力**: アーカイブのワールド名 `world`、稼働中 `creative`
  - **期待結果**: 名前の不一致が真。復元先の選択肢が 2 つ提示され、既定が「アーカイブのワールド名で復元」
  - **信頼性**: 🟡 *REQ-112。複数ワールド対応で新たに生じた経路*

- [ ] **TC-008-07**: 全展開せずに `level.dat` を読む **I** 🟡
  - **入力**: 大きなアーカイブに対する事前確認
  - **期待結果**: 一時ディレクトリにファイルが作成されない（アーカイブ内の単一エントリのみを開く）
  - **信頼性**: 🟡 *NFR-001（メモリ一定）と副作用なしの要求からの推測*

- [ ] **TC-008-08**: 副作用がない **I** 🟡
  - **入力**: 事前確認の実行前後で `data/` のファイル一覧とタイムスタンプを比較
  - **期待結果**: 一切変化しない。`fakecompose` に呼び出しが記録されない
