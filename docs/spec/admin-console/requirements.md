# admin-console 要件定義書

**要件名**: Minecraft サーバー管理コンソール（`mcadmind`）
**作成日**: 2026-09-09
**対象バージョン**: v1

## 概要

Raspberry Pi 5 (4GB) 上で `docker compose` により常時稼働している Paper サーバー（`itzg/minecraft-server`）を、
ブラウザから管理するための Web コンソールを構築する。

現在、バックアップ・復元は `docs/backup-restore.md` に書かれた**手作業のシェル手順**としてのみ存在し、
以下の問題を抱えている。

- **自動化されていない**: `save-off` → `save-all` → `zip` → `save-on` を毎回手で打つ。`save-on` を忘れると **以降の変更がディスクに書かれなくなるが、症状が何も出ない**
- **世代管理がない**: ローテーション・保持世代数・スケジュールのいずれも存在しない
- **複数ワールドの仕組みがない**: ワールドは `data/world/` の 1 つだけで、切り替え手段も命名規約もメタデータもない
- **復元が事故りやすい**: 「上書きではなく退避してから展開」という手順を人間が正しく守る必要がある。バージョンのアップグレードは片道で、間違えると戻せない

これらを、Vite + React + TypeScript + Tailwind のフロントエンドと Go + Connect RPC のバックエンドで置き換える。
バックエンドは Pi 上に systemd で常駐する単一の静的バイナリで、フロントエンドのビルド成果物も自身が配信する。
到達制御は Tailscale、認可は共有トークンの二段構えとする。

## スコープ

**v1（本要件の対象）**

1. バックアップの取得・一覧・削除・世代管理
2. バージョン検証つきの復元
3. 複数ワールドの一覧・新規作成・複製・リネーム・削除・切替
4. サーバーの起動・停止・状態表示

**v2 以降（本要件では作らない）**
コンソール / RCON パススルー UI、プレイヤー管理（op / whitelist / ban / kick）、TPS・メモリのライブグラフ、
`.env` 設定編集 UI、マルチユーザー認証 / RBAC、バックアップのオフサイト自動転送、バックアップのスケジュール実行。

## 機能要件（EARS 記法）

**【信頼性レベル凡例】**
- 🔵 **青信号**: 既存 docs・`compose.yaml`・実測値・ユーザーヒアリングを参考にした確実な要件
- 🟡 **黄信号**: 既存 docs・実測値・ヒアリングから妥当な推測による要件
- 🔴 **赤信号**: 既存資料にない推測による要件

### 通常要件

#### サーバー制御・状態表示

- **REQ-001**: システムは、コンテナの状態（実行中 / 停止 / 再起動中 / 不在）、ヘルスチェックの結果、起動時刻、`.env` の `MC_VERSION`、稼働中のワールド名、そのワールドの `level.dat` から読んだバージョン、オンライン人数と最大人数を 1 つの画面に表示しなければならない 🔵 *`README.md` の「状態は `docker compose ps` の STATUS が `Up ... (healthy)` かどうかで判断できます」およびヒアリング（v1 スコープに「サーバー起動/停止/状態表示」を選択）より*
- **REQ-002**: システムは、サーバーの起動・停止・再起動を画面から実行できなければならない 🔵 *ヒアリングより*

#### バックアップ

- **REQ-003**: システムは、保管済みバックアップの一覧を、ファイル名・サイズ・作成日時・対象ワールド名・`level.dat` から読んだバージョンとともに表示しなければならない 🔵 *ヒアリング（v1 スコープに「バックアップ取得・一覧・削除」を選択）より*
- **REQ-004**: システムは、稼働中のワールド・`data/plugins/`・`data/config/`・`data/bukkit.yml`・`data/spigot.yml` を 1 つの zip アーカイブに格納しなければならない。**この 5 項目はバックアップ対象の網羅列挙であり、`data/` 配下のこれ以外のパスをアーカイブに含めてはならない** 🔵 *`docs/backup-restore.md` のバックアップ対象表（`libraries/`・`versions/`・`cache/`・`*.jar`・`logs/`・`server.properties`・`ops.json`・`whitelist.json` を「不要」と明記）+ `docs/raspberry-pi.md` が `spigot.yml` の手編集を指示している事実より（既存の欠落の修正）*
- **REQ-005**: システムは、バックアップを個別に削除できなければならない 🔵 *ヒアリングより*
- **REQ-006**: システムは、バックアップ取得の成功直後に保持ポリシー（世代数・日数）を適用し、条件を満たさないバックアップを自動削除しなければならない 🔵 *ヒアリング（v1 スコープに「世代管理」を含む）+ `docs/backup-restore.md` に保持の記述が皆無である事実より*
- **REQ-007**: システムは、バックアップのファイル名を `backup-<MC_VERSION>-<ワールド名>-<YYYYmmdd-HHMMSS>[-<メモ>].zip` の形式で生成しなければならない 🔵 *`docs/backup-restore.md`「バックアップのファイル名にバージョンを入れておく」より。ワールド名の追加は複数ワールド対応に伴う拡張*

#### 復元

- **REQ-008**: システムは、復元の実行前に、副作用を伴わない事前確認（プリフライト）の結果として、対象バックアップのバージョン・現在のワールドのバージョン・両者の比較結果・ワールド名の一致状況・警告文の一覧をユーザーに提示しなければならない 🔵 *`docs/backup-restore.md`「バージョンとの関係」節およびヒアリング（v1 スコープに「復元」を選択）より*
- **REQ-009**: システムは、バックアップから現在のワールドを復元しなければならない 🔵 *ヒアリングより*
- **REQ-010**: システムは、復元時に退避した旧ワールドディレクトリを一覧表示し、ユーザーの操作で削除できなければならない 🟡 *`docs/backup-restore.md`「問題なく動くことを確認してから、退避した `data/world.broken-*` を削除する」を画面操作に落とした妥当な推測*

#### ワールド管理

- **REQ-011**: システムは、`data/` 配下のワールドを一覧表示し、各ワールドについて名前・稼働中か否か・サイズ・最終プレイ日時・`level.dat` から読んだバージョンを示さなければならない 🔵 *ヒアリング（v1 スコープに「複数ワールド管理・切替」を選択）+ `level.dat` の実測値（`LevelName` / `LastPlayed` / `DataVersion` が取得可能であることを確認済み）より*
- **REQ-012**: システムは、稼働させるワールドを切り替えられなければならない 🔵 *ヒアリング + itzg ドキュメントの `LEVEL` 変数（"You can either switch between world saves ... by using the LEVEL option"）より*
- **REQ-013**: システムは、新しいワールドを作成できなければならない 🔵 *ヒアリングより*
- **REQ-014**: システムは、既存のワールドを別名で複製できなければならない 🔵 *ヒアリングより*
- **REQ-015**: システムは、ワールドの名前を変更できなければならない 🔵 *ヒアリングより*
- **REQ-016**: システムは、ワールドを削除できなければならない 🔵 *ヒアリングより*

#### 操作の進捗管理（横断）

- **REQ-017**: システムは、完了までに時間を要するすべての操作（サーバーの起動・停止・再起動、バックアップの取得・復元、ワールドの切替・作成・複製・リネーム・削除）を、識別子を持つサーバー側のリソースとして管理しなければならない 🟡 *`stop_grace_period: 60s` と Paper の起動時間から、操作が分単位でかかりブラウザのリロードを跨ぐという推測*
- **REQ-018**: システムは、進行中の操作について、現在のステップ番号・総ステップ数・ステップ名・ログ行・（判明する場合は）処理済みバイト数と総バイト数を、逐次クライアントへ配信しなければならない 🟡 *上記からの妥当な推測*
- **REQ-019**: システムは、操作の識別子を保持していないクライアントに対しても、進行中の操作があればそれを取得する手段を提供しなければならない 🟡 *別端末からのアクセスや localStorage 消去を想定した妥当な推測*
- **REQ-020**: システムは、直近に完了した操作の履歴を参照できなければならない 🟡 *復元の結果を後から確認したいという妥当な推測*

#### 認証

- **REQ-021**: システムは、すべての RPC 呼び出しについて、`.env` に設定された `ADMIN_TOKEN` と一致する Bearer トークンを要求しなければならない 🔵 *ヒアリング（認証方式に「共有トークン」を選択）より*

### 条件付き要件

#### 排他制御

- **REQ-101**: いずれかの操作が実行中である場合、システムは新たな操作の開始要求を拒否し、その理由を呼び出し元に返さなければならない 🟡 *バックアップ・復元・ワールド切替・起動停止がすべて `data/` を変更するため、同時実行が破損を招くという妥当な推測*
- **REQ-102**: 操作を開始する場合、システムは `data/` 配下のロックファイルに操作の識別子・種別・プロセス ID・開始時刻・保存を停止したか否かを記録しなければならない 🟡 *プロセスの再起動を跨いで中断を検出するための妥当な推測*

#### 保存の停止と再開

- **REQ-103**: 稼働させたまま（HOT）バックアップを取得する場合、システムはアーカイブの作成前に `save-off` と `save-all` を、作成後に `save-on` を実行しなければならない 🔵 *`docs/backup-restore.md`「稼働させたまま取る」節より*
- **REQ-104**: アーカイブの作成が失敗した場合であっても、システムは `save-on` を必ず実行しなければならない 🔵 *`docs/backup-restore.md`「`save-on` を忘れると以降の変更がディスクに書かれない。スクリプトにするなら `trap` で必ず戻すこと」より*
- **REQ-105**: バックエンドのプロセスが起動した場合、システムは無条件に `save-on` を送信しなければならない 🟡 *`save-off` を残したままプロセスが異常終了する経路が存在し、RCON に「保存が有効か」を問い合わせる手段がないため、冪等な `save-on` を無条件再送するという妥当な推測*
- **REQ-106**: コンテナの状態が「ヘルスチェック不合格」から「ヘルスチェック合格」へ遷移した場合、システムは `save-on` を再送信しなければならない 🟡 *REQ-105 の時点でコンテナが停止していれば送信が失敗するため、その補償としての妥当な推測*
- **REQ-107**: バックエンドのプロセスが起動した際に、前回の実行で残されたロックファイルを検出した場合、システムは「中断された操作がある」ことを状態情報に含め、そのロックファイルを削除しなければならない 🟡 *上記からの妥当な推測*

#### シードの後始末

- **REQ-108**: `docker compose up -d` を伴う操作を開始する場合、システムは `.env` の `MC_SEED` を無条件に空へ戻さなければならない。ワールドの新規作成のみ、その直後に指定されたシードを書き込む 🟡 *新規作成の完了待ちは最大 900 秒に及び、その間にプロセスが停止すると `.env` にシードが残って次回以降の起動に見えない形で影響するという推測。`save-on` の無条件再送と同じ自己修復パターンを採る*

#### バージョン検証

- **REQ-109**: 復元対象のバックアップに含まれるワールドの `DataVersion` が、現在のワールドの `DataVersion` と一致しない場合、システムは警告を提示し、ユーザーの明示的な承諾がない限り復元を実行してはならない 🔵 *`docs/backup-restore.md`「ワールドのアップグレードは片道」「`MC_VERSION` を上げた後に古いバックアップを復元すると、再び同じアップグレードが走る」より*
- **REQ-110**: バックアップに含まれるワールドの `DataVersion` が現在のワールドより小さい場合、システムは「復元後に片道アップグレードが再度実行される」旨を警告しなければならない 🔵 *同上*
- **REQ-111**: バックアップに含まれるワールドの `DataVersion` が現在のワールドより大きい場合、システムは「現在の `MC_VERSION` では開けない可能性が高い」旨を警告しなければならない 🔵 *`docs/backup-restore.md`「新しいバージョンで保存されたワールドを古い `MC_VERSION` に戻すことはできない」より*
- **REQ-112**: バックアップに含まれるワールド名が現在稼働中のワールド名と異なる場合、システムはその不一致を提示し、「アーカイブのワールド名で復元する」か「現在稼働中のワールド名として復元する」かをユーザーに選択させなければならない 🟡 *複数ワールド対応により、素直に展開すると稼働中のワールドが変化せず「何も起きていないように見える」経路が生じるという推測*
- **REQ-113**: 復元の実行を要求された場合、システムはクライアントから送られた確認内容に依存せず、事前確認をサーバー側で再実行しなければならない 🟡 *クライアントの申告を信用しないという一般的な設計判断*

#### 復元の安全性

- **REQ-114**: 復元を実行する場合、システムは現在のワールドディレクトリを削除せず、`data/<ワールド名>.broken-<日時>` へ移動して退避してから、アーカイブを展開しなければならない 🔵 *`docs/backup-restore.md`「『上書き』ではなく『消してから展開』」「`rm` ではなく `mv` で退避しておくと、復元に失敗しても戻せる」より*
- **REQ-115**: アーカイブの展開が失敗した場合、システムは展開途中のディレクトリを削除し、退避したディレクトリを元の位置へ戻し、サーバーを起動し直したうえで、操作を失敗として記録しなければならない 🟡 *REQ-114 の「失敗しても戻せる」を自動化した妥当な推測*
- **REQ-116**: 復元が成功した場合であっても、システムは退避したディレクトリを自動削除してはならない 🔵 *`docs/backup-restore.md`「問題なく動くことを確認してから、退避した `data/world.broken-*` を削除する」より*

#### ワールドの切替

- **REQ-117**: ワールドを切り替える場合、システムは、サーバーを停止し、`.env` の `MC_LEVEL` を書き換え、`docker compose up -d` によってコンテナを再作成しなければならない 🔵 *`README.md`「`docker compose restart` ではなく `docker compose up -d` を使ってください。`.env` の変更はコンテナの再作成で反映されます」および `OVERRIDE_SERVER_PROPERTIES=TRUE` の帰結より*
- **REQ-118**: ワールドを切り替える場合、システムは切替前のワールドのディレクトリを移動・削除してはならない 🔵 *`LEVEL` 方式ではディレクトリが兄弟として並存するという itzg ドキュメントの記述より*
- **REQ-119**: 指定されたワールドが現在稼働中のワールドと同一である場合、システムは何も変更せずに操作を成功として完了しなければならない 🟡 *冪等性を確保するための妥当な推測*
- **REQ-120**: 稼働中のワールドを複製する場合、システムは複製の前に `save-off` と `save-all` を実行し、複製の完了後に `save-on` を実行しなければならない 🟡 *HOT バックアップと同じ理由（書き込み途中の region ファイルを掴むと壊れたコピーになる）による妥当な推測*
- **REQ-121**: ワールドを複製する場合、システムは複製元の `session.lock` を複製先に含めてはならない 🟡 *`docs/backup-restore.md`「`session.lock` は起動時に作り直される」から、複製先に持ち込む意味がないという推測*

#### 入力の検証と確認

- **REQ-122**: ワールド名が指定された場合、システムは `^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$` に一致することを検証し、予約名（`.`、`..`、`logs`、`plugins`、`config`、`cache`、`libraries`、`versions`）および `.broken-` を含む名前を拒否しなければならない 🟡 *`data/` の実際のディレクトリ構成（`logs` / `plugins` / `config` / `cache` / `libraries` / `versions` が兄弟として存在する）と退避命名規約から導いた推測*
- **REQ-123**: ワールドの削除または復元を要求された場合、システムは対象の名称の完全一致入力を確認として要求しなければならない 🟡 *不可逆な操作に対する一般的な安全策*
- **REQ-124**: 稼働中のワールドの削除を要求された場合、システムはこれを拒否し、先に別のワールドへ切り替えるよう案内しなければならない 🟡 *稼働中のディレクトリを消すと復旧できないという妥当な推測*

#### 設定ファイルの取り扱い

- **REQ-125**: `.env` を書き換える場合、システムは読み込み時点の更新時刻とサイズが書き込み直前も一致することを確認し、一致しない場合は書き込みを中止して「外部から変更された」旨を返さなければならない 🟡 *`README.md` が `vi .env` による手編集を正規の手順として案内しており、人間の編集を潰してはならないという推測*
- **REQ-126**: `.env` を書き換える場合、システムは一時ファイルへ書き出して同期したうえで名前を変更する方式を用い、一時ファイルは元ファイルと同じパーミッションで作成しなければならない 🟡 *`.env` が `RCON_PASSWORD` を保持しており、書き込み途中での電源断や権限の緩みを避けるという推測*

#### 進捗の配信

- **REQ-127**: クライアントが進捗の購読を開始する際に開始位置を指定した場合、システムはその位置以降の記録済みイベントを再送してから、以後のイベントの配信を続けなければならない 🟡 *ブラウザのリロード後に「スピナーだけが表示される」状態を避けるための推測*
- **REQ-128**: 進捗の配信が中断された場合、クライアントは最後に受信した位置の次から購読を再開しなければならない 🟡 *REQ-127 と対になる妥当な推測*

### 状態要件

- **REQ-201**: いずれかの操作が実行中である間、画面はすべての変更を伴う操作の実行手段を無効化しなければならない 🟡 *サーバー側の排他（REQ-101）を UI に反映するという妥当な推測*
- **REQ-202**: コンテナが停止している間、システムは RCON を伴う手順（`save-off` / `save-all` / `save-on` / オンライン人数の取得）を省略し、そのことを理由に操作を失敗させてはならない 🟡 *停止中のサーバーに RCON で接続できないという自明の制約からの推測*
- **REQ-203**: 中断された操作が検出されている間、画面はその旨の警告を表示し続けなければならない 🟡 *REQ-107 を UI に反映するという妥当な推測*
- **REQ-204**: バックアップが 1 件も存在しない間、画面はその旨と最初のバックアップを取得する手段を提示しなければならない 🟡 *現在バックアップが 0 件であるという実測からの妥当な推測*

### オプション要件

- **REQ-301**: システムは、サーバーを停止してからバックアップを取得する方式（COLD）を選択肢として提供してもよい 🔵 *`docs/backup-restore.md`「停止してから取る（確実・推奨）」より。ヒアリングで既定は HOT と確定したため、COLD は選択肢の位置づけ*
- **REQ-302**: システムは、バックアップに短いメモを付与し、ファイル名に反映してもよい 🟡 *「バージョンを上げる前のバックアップ」等を識別したいという推測*
- **REQ-303**: システムは、ワールドの新規作成時にシード値の指定を受け付けてもよい 🔵 *`docs/backup-restore.md`「`level-seed` を指定したい場合は `compose.yaml` の `environment` に `SEED` を追加する」より*
- **REQ-304**: システムは、世代数に加えて日数によるバックアップの保持条件を提供してもよい 🟡 *世代数だけでは「古すぎるものを消したい」に対応できないという推測*
- **REQ-305**: システムは、退避されたワールドディレクトリを一定日数経過後に自動削除してもよい 🟡 *退避が溜まると 30MB 単位でディスクを圧迫するという推測*

### 制約要件

#### セキュリティ・秘匿情報

- **REQ-401**: システムは、RCON のポート 25575 を公開してはならない 🔵 *`README.md`「**`ports` に `25575` を足さないでください。**」（RCON は平文プロトコルで、暗号化も総当たり保護もない）より*
- **REQ-402**: システムは、RCON コマンドを `docker compose exec -T mc rcon-cli <コマンド>` の形式で実行しなければならない 🔵 *`README.md`「`docker compose exec mc rcon-cli` は**コンテナ内の** `rcon-cli` を起動し、それが同じコンテナ内のサーバーへ RCON で接続します」より*
- **REQ-403**: システムは、`data/server.properties` をバックアップアーカイブに含めてはならず、その内容を API から返してもよい項目は明示的な許可リストに限定しなければならない 🔵 *`data/server.properties` が `rcon.password` と `management-server-secret` を平文で保持していることを実測で確認。加えて `docs/backup-restore.md` が「毎回 `.env` から再生成される」ためバックアップ不要としている*
- **REQ-404**: システムは、アーカイブの展開において、`data/` 以外を指すエントリ、上位ディレクトリへの参照を含むエントリ、絶対パスのエントリ、シンボリックリンクのエントリを、展開の開始前に拒否しなければならない 🟡 *zip 展開における一般的な脆弱性（zip-slip）への対策*
- **REQ-405**: システムは、ファイルシステム上のパスを構築する際に、結果が `data/` の配下に収まることを検証しなければならない 🟡 *パストラバーサルへの一般的な対策*
- **REQ-406**: システムは、`ADMIN_TOKEN` の比較を、値の内容によって処理時間が変化しない方法で行わなければならない 🟡 *トークン比較におけるタイミング攻撃への一般的な対策*
- **REQ-407**: システムは、単方向ストリーミングの RPC についても、単項の RPC と同一の認証を適用しなければならない 🟡 *Connect の単項用インターセプタだけではストリーム RPC が認証を経由しないという実装上の落とし穴への対策*
- **REQ-408**: システムは、`ADMIN_TOKEN` が 32 文字未満である場合、起動時に異常終了し、エラーメッセージに生成コマンド（`openssl rand -hex 32`）を含めなければならない 🟡 *`compose.yaml` が `MC_VERSION` と `RCON_PASSWORD` に対して `:?` による fail-fast を採用していることに倣った推測*

#### 既存構成との整合

- **REQ-409**: システムは、バックアップおよび復元の対象となるワールドを `.env` の `MC_LEVEL` から決定しなければならない。`world` という名前を固定値として扱ってはならない 🟡 *複数ワールド対応の帰結。既存手順は `data/world` を固定値として扱っている*
- **REQ-410**: システムは、`.env` を書き換える際に、既存のコメント行・空行・行内コメント・引用符の付与方針を保存しなければならない 🔵 *`.env` に 18 行以上の日本語コメントがあり、`docs/backup-restore.md` が「`.env` の値のうち空白を含むものは `MC_MOTD="..."` のようにクォートしてある。クォートを外すと `source` が失敗する」と明記していることより*
- **REQ-411**: システムは、`docker compose` を呼び出す際に、プロジェクトディレクトリ・プロジェクト名・compose ファイルのパスを明示的に指定しなければならない 🟡 *systemd 配下では作業ディレクトリがリポジトリと一致せず、プロジェクト名を省略すると手動操作とは別プロジェクトのコンテナが起動するという推測*
- **REQ-412**: システムは、ワールドのバージョン判定に `level.dat` の `Data.DataVersion`（整数）を用いなければならない。表示文字列 `Data.Version.Name` を判定の根拠としてはならない 🔵 *`level.dat` を直接デコードし、`DataVersion=4903` / `Version.Name="26.2"` の双方が存在することを確認済み*
- **REQ-413**: システムは、バックアップのファイル名に記録されたバージョンやワールド名を、真の値として扱ってはならない。真の値は常にアーカイブ内の `level.dat` から取得しなければならない 🟡 *ファイル名は人間が改名でき、旧形式（`backup-<版>-<日時>.zip`）も存在しうるという推測*

#### 動作環境

- **REQ-414**: システムは、単一の静的バイナリとして linux/arm64 上で動作し、フロントエンドのビルド成果物を自身に埋め込んで配信しなければならない 🔵 *ヒアリング（実行形態に「Pi 上に systemd 常駐」を選択）より*
- **REQ-415**: システムは、アーカイブの作成・展開・ワールドの複製において、ファイルの内容全体をメモリ上に保持してはならない 🔵 *`docs/raspberry-pi.md` の「実 RSS はヒープの 1.3〜1.4 倍 ≒ 2.7GB」「OS に約 600MB 残す」という記述より、4GB 機で MC と共存する制約*
- **REQ-416**: システムは、`docker compose` および RCON の呼び出しを、差し替え可能な境界の背後に隔離しなければならない 🟡 *カバレッジ 80% 以上（ユーザーのグローバル開発ルール）を実機なしで達成するための推測*

#### スコープの制約

- **REQ-417**: システムは、進行中の操作を中断する手段を提供してはならない 🟡 *復元の途中で中断すると「退避済みかつ展開途中」という最も復旧が困難な状態を作るという推測。v1 の明示的な設計判断*
- **REQ-418**: システムは、バックアップを他のホストへ転送してはならない 🔵 *ヒアリング（オフサイト退避に「v1 はローカルのみ」を選択）より*
- **REQ-419**: システムは、バックアップの一覧画面において、バックアップがサーバーと同一のディスク上にしか存在しないことを常時明示しなければならない 🔵 *`docs/backup-restore.md`「同じ Mac の中に置いているだけでは、ディスク障害で本体もろとも消える」+ ヒアリングでオフサイトを v1 対象外としたことより*

## 非機能要件

### パフォーマンス

- **NFR-001**: アーカイブの作成・展開およびワールドの複製は、固定長のバッファによるストリーミング処理で行い、処理対象の総量にかかわらずメモリ使用量が一定でなければならない 🔵 *`docs/raspberry-pi.md` のメモリ収支より（REQ-415 の具体化）*
- **NFR-002**: アーカイブの圧縮は速度優先の設定を用いなければならない 🟡 *`.mca` 形式が内部で既に zlib 圧縮されており、Pi の CPU で最大圧縮を行っても縮まないという推測*
- **NFR-003**: サーバーの停止完了の待機は最大 90 秒、既存ワールドでの起動完了の待機は最大 300 秒、ワールドの新規生成を伴う起動完了の待機は最大 900 秒とする 🟡 *`compose.yaml` の `stop_grace_period: 60s` と `README.md` に記載された `Done (11.800s)!` の実績、および Pi でのワールド生成が長時間に及ぶという推測*
- **NFR-004**: 一覧画面の表示に必要な情報の取得は、ワールドおよびバックアップの実体を全走査せずに完了しなければならない 🟡 *30MB のワールドが複数ある想定での妥当な推測*

### セキュリティ

- **NFR-101**: 管理コンソールへの到達は Tailscale の tailnet 内に限定され、その上でトークンによる認可を行う二段構えとしなければならない 🔵 *`docs/raspberry-pi.md`「tailnet に参加している端末からしか到達できない」+ ヒアリング（共有トークンを選択）より*
- **NFR-102**: 管理コンソールの待ち受けアドレスの既定値は、Tailscale のインタフェースから到達可能でなければならない 🟡 *`compose.yaml` が 25565 を `0.0.0.0` にバインドしている理由と同一。ループバックに限定すると Pi 上の systemd で常駐させたとき別端末のブラウザから開けない*
- **NFR-103**: 配信する HTML には、外部からのスクリプト読み込みおよび外部への通信を禁止するコンテンツセキュリティポリシーを付与しなければならない 🟡 *トークンをブラウザに保持する設計におけるリスク緩和策*
- **NFR-104**: エラー応答は、内部の実装詳細・ファイルパス・秘匿情報を含んではならない 🟡 *一般的なセキュリティ要件*

### ユーザビリティ

- **NFR-201**: 画面に表示される文言、および進捗のステップ名・ログは日本語でなければならない 🔵 *リポジトリのドキュメント・コメント・コミットメッセージがすべて日本語であるという実測より*
- **NFR-202**: 画面を再読み込みしても、進行中の操作の進捗表示とそれまでのログが失われてはならない 🟡 *復元が分単位でかかりリロードを跨ぐという推測（REQ-127 の利用者側の要件）*
- **NFR-203**: 不可逆な操作については、実行前にその影響（何が失われ、何が残るか）を明示しなければならない 🟡 *`docs/backup-restore.md` が復元手順に対して繰り返し警告を置いていることに倣った推測*
- **NFR-204**: ワールドの切替画面は、切替前のワールドが削除されずいつでも戻せることを明示しなければならない 🟡 *「切り替え」という語から削除を連想する利用者への配慮という推測*

### 保守性・テスト容易性

- **NFR-301**: テストカバレッジは、生成されたコードを除いて 80% 以上でなければならない 🔵 *ユーザーのグローバル開発ルールより*
- **NFR-302**: 各ソースファイルは 800 行を超えてはならず、各関数は 50 行を超えてはならない 🔵 *ユーザーのグローバル開発ルールより*
- **NFR-303**: 状態を表すデータ構造は、変更ではなく新しい値の構築によって更新しなければならない 🔵 *ユーザーのグローバル開発ルールより*
- **NFR-304**: ワールド名の検証規則は、フロントエンドとバックエンドで同一の定義を用い、両者にその一致を確認するテストを置かなければならない 🟡 *片方だけが緩むと不正な名前がファイルシステムに到達するという推測*

## Edge ケース

### エラー処理

- **EDGE-001**: `level.dat` が読み取れない、または想定した構造を持たない場合、システムはバージョンを「不明」として扱い、当該ワールド・バックアップの一覧表示自体は継続しなければならない 🟡 *破損したワールドや将来の形式変更に対する妥当な推測*
- **EDGE-002**: オンライン人数を取得するコマンドの出力が解釈できない場合、システムは人数を「不明」として表示し、状態取得そのものを失敗させてはならない 🟡 *出力書式がサーバーのバージョンに依存するという推測*
- **EDGE-003**: コンテナ状態の取得結果が想定した構造と異なる場合、システムは解釈できたフィールドのみを用い、未知のフィールドを無視しなければならない 🟡 *`docker compose ps --format json` の出力形状が Compose のバージョンで変わるという推測*
- **EDGE-004**: ログからの起動完了の検出が成立しない場合、システムはヘルスチェックの合格をもって起動完了と判定しなければならない 🟡 *ログのローテーションやバッファリングにより検出が失敗しうるという推測*
- **EDGE-005**: 復元中にバックエンドのプロセスが異常終了した場合、次回起動時にシステムは中断を検出して警告し、退避されたディレクトリを一覧に表示しなければならない 🟡 *REQ-107 と REQ-116 の組み合わせによる妥当な推測*
- **EDGE-006**: ワールドの複製先または展開先に十分な空き容量がない場合、システムは処理を開始する前に中止しなければならない 🟡 *途中で容量が尽きると中途半端なディレクトリが残るという推測*
- **EDGE-007**: 稼働中のワールドのディレクトリが存在しない状態で切替を要求された場合、システムはその旨を記録したうえで処理を継続し、サーバーによる新規生成に委ねなければならない 🟡 *`LEVEL` を未生成の名前に向けると Paper が生成するという itzg ドキュメントの記述からの推測*
- **EDGE-008**: バックアップの保管先ディレクトリが存在しない場合、システムはこれを作成しなければならない 🟡 *初回起動時の妥当な推測*

### 境界値

- **EDGE-101**: ワールド名が 1 文字の場合は受理し、33 文字の場合は拒否しなければならない 🟡 *REQ-122 の正規表現の境界*
- **EDGE-102**: ワールド名が空文字、または `data/` 配下の既存ディレクトリ名（`logs`・`plugins`・`config`・`cache`・`libraries`・`versions`）と一致する場合、拒否しなければならない 🔵 *`data/` の実際の構成を実測で確認済み*
- **EDGE-103**: 保持ポリシーの適用によってすべてのバックアップが削除条件を満たす場合であっても、システムは最も新しい 1 世代を必ず残さなければならない 🟡 *保持ポリシーの誤設定によって全損する経路を塞ぐという推測*
- **EDGE-104**: 保持世代数に 0 以下が指定された場合、システムはこれを拒否しなければならない 🟡 *EDGE-103 と同趣旨の推測*
- **EDGE-105**: 複製先または改名先の名前が既存のワールドと重複する場合、システムは処理を開始する前に拒否しなければならない 🟡 *既存ワールドの意図しない上書きを防ぐという推測*
- **EDGE-106**: 進捗のイベントが保持上限を超えた場合、システムは古いイベントから破棄しなければならず、その際に最新の状態が失われてはならない 🟡 *メモリ上限を設けつつ、リロード後に最新状態を復元できる必要があるという推測*
