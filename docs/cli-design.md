# CLI 化の設計（cobra）

`mcadmind` に常駐モードと CLI モードを持たせ、ブラウザを開かずにワールドや
バックアップを操作できるようにするための設計。実装前の調査と方針を残す。

画面から何が呼ばれるかは [spec/admin-console/sequences.md](spec/admin-console/sequences.md)、
公開運用に関わる論点は [security-review.md](security-review.md) にある。

---

## なぜ入れやすいか

土台はすでにその形になっている。調べた結果は次のとおり。

- **ユースケース層が HTTP を知らない。** `worldctl.UseCase` などはポート
  （インターフェース）越しにしか外と繋がらず、`rpc.NewWorldHandler(d.worlds)` は
  薄い翻訳層でしかない。CLI からは同じ `d.worlds` を直接呼べる。
- **層の依存が機械的に守られている。** `internal/archtest` が上位層への逆流を
  検査しているので、CLI を足しても土台が崩れにくい。
- **配線が 1 箇所にある。** `cmd/mcadmind/build.go` がすべてを組み立てており、
  しかも `buildDeps`（インフラとユースケース）と `buildServer`（HTTP だけ）に
  分かれている。**CLI は前者だけを使えばよい。**
- `main.go` の `run(args, stdout)` は副作用から切り離してあるので、
  `flag` を cobra に差し替える作業は機械的で、既存のテストもそのまま活きる。

## コマンド体系

```
mcadmind serve                             # 常駐（今の挙動）
mcadmind status                            # 状態の表示
mcadmind world list|switch|create|clone|rename|delete
mcadmind backup list|create|restore|prune
```

共通フラグは `--project-dir`（既定 `.`）と `--log-level`。

`serve` を既定の副コマンドにはしない。引数なしの実行が常駐の開始になると、
CLI のつもりで叩いた端末がサーバーを抱えたまま残る。

**取り消せない操作には、画面と同じ関門を CLI にも置く。** ワールドの削除と
復元は `--confirm-name <名前>` の完全一致を要求する。画面側が入力を求めているのは
押し間違いを防ぐためで（REQ-123）、CLI だけ素通りさせると守りの意味がなくなる。

---

## 実行方式：デーモン経由を既定にする

CLI が操作を実行する方法は 2 つある。**どちらを既定にするかが、この設計で
いちばん大きな判断になる。**

| | 案 A：直接ユースケースを叩く | 案 B：動作中のデーモンの API を叩く |
|---|---|---|
| デーモン停止中 | 使える | 使えない |
| 進捗が画面に出るか | **出ない** | 出る |
| 操作履歴 | プロセスごとに分断 | 一元化される |
| 排他 | ロックファイル頼み | デーモン内で完結 |

**既定は案 B、`--local` で案 A に落とす。** 理由は次の「落とし穴 1」にある。
`--local` を残すのは、デーモンが起動しない状態（設定ミスやフロント未ビルド）でも
復旧操作ができるようにするため。

---

## `build()` の分割

現在の `build()` には常駐モード専用の前提が 3 つ混ざっている。CLI 経路では
どれも通してはいけない。

| 箇所 | いま何が起きるか | CLI ではどうするか |
|---|---|---|
| `webui.IsBuilt()` | フロント未ビルドだと起動そのものが失敗する | `serve` だけで確認する |
| `loadSettings()` の `ADMIN_TOKEN` 必須 | ローカル実行に不要な設定を強制される | `serve` だけで要求する |
| `app.Run()` の `reconciler.RunOnce()` | **CLI を叩くたびに save-on が飛ぶ** | CLI では呼ばない（下記） |

設定の読み込みは、`ADMIN_TOKEN` の検証だけを `serve` 側へ寄せる。`ADMIN_ADDR` や
`ADMIN_DOCKER_BIN` は CLI でも要る。

## 並行実行：安全に弾かれる

**サーバー起動中に CLI を実行してよい。** 排他はプロセスをまたいで効く。

`operations.Manager` は操作の開始時に `data/.admin-console.lock` を
`O_CREATE|O_EXCL` で作る（`infrastructure/persistence/lockfile`）。プロセス内の
Mutex と二段構えになっている。

- デーモンがバックアップ中に CLI で `world switch` を叩くと、CLI 側が
  「他の操作が実行中です」で即座に落ちる。**data/ は壊れない。**
- 逆も同じ。CLI が復元中なら画面の変更ボタンは弾かれる。
- ロックには PID が入っていて生存確認される。CLI を Ctrl-C で殺してロックが
  残っても、次回起動時に「中断された操作」として検出される。
- 起動時の回復処理は、**生きているプロセスのロックを奪わない**
  （`IsStale` が偽なら警告を出すだけ）。

### 落とし穴 1：CLI の操作は画面から見えない

進捗（`Operation`）は各プロセスのメモリ内にある。`GetActiveOperation` は自分の
メモリしか見ないため、CLI が別プロセスで復元を走らせても**デーモンは「操作なし」と
答え続ける**。画面は 5 秒ごとに探しに行くが見つからない。

結果、**ボタンは押せる状態に見えるのに、押すと弾かれる**という、理由が画面から
読めない状態になる。壊れはしないが、運用中に一番困る種類の分かりにくさになる。

案 B（デーモン経由）を既定にすれば、この問題は起きない。案 A を使う場合は、
最低限 `GetStatus` に `Lock.Inspect()` の結果を混ぜ、「別のプロセスが操作中」
であることを画面に出すこと。

### 落とし穴 2：`RunOnce` の save-on が hot バックアップを壊しうる

**これは実害がある。CLI 化の前に直す価値がある。**

`reconcile.Reconciler.RunOnce()` は**無条件に save-on を送る**。一方 `Loop` の側は
`savingIsIntentionallyOff()` で「いま save-off 中の操作があるか」をロックから
確認して抑止している。この判定が `RunOnce` には入っていない。

デーモンが hot バックアップ中（save-off のまま zip を固めている最中）に別プロセスが
起動して `RunOnce` が走ると、**書き込み途中の region ファイルが zip に取り込まれ、
静かに壊れたバックアップができる**。`reconcile.go` のコメント自身が、この事故を
`Loop` 側で警戒している。

対応は 2 段階で考える。

1. CLI 経路では `RunOnce` を呼ばない（最低限）。
2. `RunOnce` にも `savingIsIntentionallyOff()` の判定を入れる（本筋）。
   デーモンを多重起動した場合にも同じ事故が起きるため、こちらの方が守りが広い。

### 落とし穴 3：`.env` の読み書き（軽微）

`dotenv` の書き込みは一時ファイルと `os.Rename` で原子的。ただし
「読む → 書き換える → 書き戻す」の間は保護されていない。

現状、`.env` を書き換える操作（`MC_LEVEL` の変更など）はすべて操作ロックの下で
走るので競合しない。**ロックを取らない設定変更コマンド（`mcadmind config set` の
ようなもの）を足すと、そこで初めて競合しうる。** 足すなら操作ロックを取ること。

## 進め方

1. `RunOnce` の save-on 抑止を直す（CLI とは独立に価値がある）。
2. cobra を入れ、`serve` を既存の挙動そのままで切り出す。ここまでは挙動が
   変わらないので、既存の E2E がそのまま回帰試験になる。
3. 読み取り専用の副コマンド（`status`、`world list`、`backup list`）を足す。
   ロックも副作用も関係しないので、CLI の骨格を安全に固められる。
4. 変更を伴う副コマンドを足す。ここで案 B のクライアント経路と `--local` を入れる。

---

## 決めていないこと

- **出力形式。** 人が読む表と `--json` の両対応にするか。運用スクリプトから
  使うなら要るが、v1 の用途では表だけで足りるかもしれない。
- **`--local` での進捗表示。** 端末に手順とログをそのまま流すか、要約だけにするか。
- **`serve` 以外での `ADMIN_ADDR` の扱い。** 案 B のクライアントが接続先を
  どこから読むか（`.env` か、専用のフラグか）。
