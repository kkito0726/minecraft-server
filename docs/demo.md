# 公開デモ

管理コンソールの画面を、バックエンド無しで触れるようにしたもの。
成果物を人に見せるとき、Pi も docker も要らずに URL ひとつで渡せる。

本物の管理画面は今までどおり Go のバイナリに同梱して Pi から配信する。
**ホスティングするのはデモだけ**で、こちらは公開されている。

---

## なぜ Pages に置けるのか

デモは**バックエンドに一切接続しない**。ブラウザの中のモックで完結するため、
[security-review.md](security-review.md) に挙げた公開時の論点がどれも発生しない。

| 論点 | デモでどうなるか |
|---|---|
| 混在コンテンツ（HTTPS から HTTP を叩けない） | 通信そのものが無い |
| CORS | 同一オリジンどころか外へ出ない |
| トークンの漏洩 | 守るべきものが存在しない |
| 版のずれ | 画面と模擬サーバーが同じ成果物に入っている |

---

## 触り方

Pages の配信先は `https://<ユーザー名>.github.io/minecraft-server/`。
リポジトリの Settings → Pages で、ソースを **GitHub Actions** にしておく必要がある。

入口のトークン画面は残してある。初期値が入っているのでそのまま「入る」でよい。
何を入れても通る。

デモであることは、画面の上端に常に出る帯で示す。閉じられない。

手元で動かすときは次のとおり。

```bash
cd frontend
npm run dev:demo      # 開発サーバー（ホットリロードあり）
npm run build:demo    # dist-demo/ に成果物を出す
```

## 仕組み

画面のコードには手を入れていない。**通信の口だけを差し替える。**

```
lib/transport.ts
  ├─ 通常:  createConnectTransport({ baseUrl: '/rpc' })   ← 実サーバー
  └─ デモ:  createRouterTransport(demo の実装)            ← ブラウザ内で完結
```

`createRouterTransport` はサービスの実装をブラウザの中でそのまま動かす。
生成された proto の型を通り、進捗の配信（server-streaming）も本物と同じ経路を
通るので、再接続や再読み込みの動きまで同じように試せる。

例外は zip の取り込みだけ。ここは Connect を通らない素の POST なので、
`features/backups/upload.ts` に別の分岐がある。

デモの中身は `src/demo/` にある。状態（`state.ts`）、手順の進行（`operations.ts`）、
各サービスの実装（`*Service.ts`）に分かれていて、proto への変換は `messages.ts` に
閉じている。

### 実物と同じにしてあるところ

見た目だけ似せると、デモを見た人が誤った理解を持ち帰る。次は実物と同じ。

- 操作は**同時にひとつしか走らない**。実行中に別の操作を始めると断られる。
- 取り消せない操作の関門。ワールドの削除と復元は名前の完全一致を要求する。
- 版が食い違う復元は、警告を読んだという承諾がなければ実行できない。
- 削除も復元も、消す前に退避する。
- 保持ポリシーは、世代数と日数の両方を満たさないものだけを消し、最新の 1 世代は必ず残す。

### 本番に混ざらないこと

`__DEMO__` はビルド時に定数へ畳まれる。通常のビルドではデモを読み込む条件が
`false` になり、動的 import ごと成果物から落ちる。

確認したいときは、ビルド後の成果物を検索すればよい。

```bash
cd frontend && npx vite build
grep -l "installDemo" ../backend/internal/presentation/webui/dist/assets/*.js   # 何も出なければよい
```
