# セキュリティ調査（管理コンソール）

管理コンソールの現状の防御と、**インターネットへ公開したくなった場合に
足りないもの**を、コードを読んで洗い出した記録。

前提の整理は [admin-console.md](admin-console.md) の「到達できる範囲」にある。
ここは、その前提が変わったときに何が壊れるかを扱う。

---

## いまの前提

到達制御と認可を分けた二段構えになっている。

| 層 | 担うもの | 破られたときに残る守り |
|---|---|---|
| Tailscale | tailnet の外から 8787 に届かせない | `ADMIN_TOKEN` |
| `ADMIN_TOKEN` | tailnet の中の他の端末・他の人を止める | なし（管理操作がすべて可能になる） |

**`ADMIN_ADDR` は `0.0.0.0:8787`。** これは「同一ネットワークからのみ」を意味する
指定ではなく、**その機械が持つすべてのネットワーク差込口で受ける**という意味。
したがって Pi の場合、tailnet だけでなく**家庭内 LAN からも到達する**。
インターネット側から届かないのは、ルーターが 8787 を転送していないからであって、
`0.0.0.0` のおかげではない。

LAN からの到達面を閉じたい場合は `ADMIN_ADDR` を Tailscale の IP
（`100.x.y.z:8787`）にする。ただし起動時にその IP が確定している必要があり、
Tailscale が上がる前に mcadmind が起動すると待ち受けに失敗する。

---

## いま効いている防御

コードを読んで確認できたもの。**同梱構成（フロントを Go のバイナリに埋め込む）
が、このうちいくつかを成立させている。**

| 防御 | 実装 |
|---|---|
| 外部スクリプトと外部通信の禁止 | CSP `default-src 'self'`（`presentation/http/static.go`） |
| クロスオリジンからの API 利用を不可 | CORS を実装していない（同一オリジン前提のため不要） |
| トークンの定数時間比較 | `crypto/subtle`（`presentation/http/auth/auth.go`） |
| 短いトークンを起動時に拒否 | 32 文字未満はエラー。生成コマンドを添えて止まる |
| ストリーム RPC も認証する | `WrapStreamingHandler` を実装（進捗の購読が素通りしない） |
| Connect の外側も同じ守り | zip の受け口を `Interceptor.Middleware` で明示的に包む |
| zip 展開の経路外書き込み防止 | `infrastructure/archive/safepath.go`（試験あり） |
| 設定の漏洩防止 | `publicConfigKeys` の許可リスト方式。`RCON_PASSWORD` と `ADMIN_TOKEN` は返さない |
| `.env` の壊れた書き込みの防止 | 一時ファイル + `os.Rename` で原子的に置換 |
| ディスクの枯渇対策 | 取り込みの上限は空き容量の半分（`backupctl/import.go`） |
| 認証前の情報漏らし防止 | 認証インターセプタをログの外側に置く。失敗したリクエストの中身を記録しない |

---

## 同梱構成そのものの評価

**フロントとバックエンドを 1 つのバイナリに入れること自体は、セキュリティ上は
むしろ有利。** 分離した場合に増えるものの方が多い。

- 同一オリジンなので **CORS が要らない**。実装がない = クロスオリジンから叩けない。
- **CSP を自分で付けられる。** 外部配信を挟むとここは配信側の設定に依存する。
- 配信物と API の版が必ず一致する。古い画面が新しい API を叩く事故が起きない。
- 攻撃面が 1 プロセス・1 ポートに収まる。Node のプロセスも前段の Web サーバーも要らない。

したがって、公開運用で変えるべきは**配信形態ではなく認証方式**になる。

---

## 公開運用に足りないもの

優先度の高い順。**1〜4 はフロントを分離しても 1 つも解決しない。**

### 1. TLS がない（重い）

平文 HTTP と h2c で動いている。`Authorization: Bearer` のトークンが平文で流れる。
到達境界を Tailscale に任せる前提だからこの選択になっている。

公開するなら、前段で TLS を終端する（Caddy など）か、Tailscale Funnel を使う。

### 2. レート制限とロックアウトがない（重い）

リポジトリ全体を確認したが、レート制限の実装はない。64 文字の hex なので総当たりは
現実的でないが、公開するなら失敗回数の制限と記録は要る。

あわせて、**`WriteTimeout` を意図的に外している**（進捗の配信が分単位で続くため、
`presentation/http/server.go` に理由が書かれている）。遅い接続を大量に張られると
枯渇しうるので、公開時は前段のプロキシで守る。

### 3. トークンが localStorage にある（重い）

XSS で即座に漏れる。現状は厳格な CSP が緩和策で、その判断は `TokenGate` の
コメントに明記されている。**公開する = CSP の前提が変わるなら、ここも一緒に変える。**
HttpOnly + Secure な Cookie セッションへ移し、CSRF 対策を入れるのが筋。

### 4. 単一の共有トークンである（重い）

利用者を区別できない。失効は `.env` の書き換えと全員の再入力。監査ログに
「誰が」を残せない。公開運用が複数人を意味するなら、ここは作り直しになる。

### 5. アップロードに絶対値の上限がない（軽い）

上限は**空き容量の半分**で決まる（包み直しで 2 倍を見込むため）。ディスクを
埋めきらない設計は正しいが、認証を通った利用者が繰り返せば圧迫はできる。
公開するなら絶対値の上限も置く。

### 6. 影響範囲がホスト全体に及ぶ（前提の重さ）

このプロセスは `docker compose` を実行できる。つまり**管理コンソールの侵害は、
ホスト上の実質的な任意コード実行に近い**。tailnet 内に閉じている今はこの前提で
釣り合っているが、公開するとリスクの重みが変わる。

---

## 公開したくなったときの順序

1. 前段で TLS を終端する。
2. レート制限と失敗の記録を入れる。
3. 認証を共有トークンから利用者つきセッションへ移す（3 と 4 は同時に直す）。
4. アップロードに絶対値の上限を置く。
5. 監査ログに「誰が」を残す。

**1 と 2 を飛ばして 3 だけを直しても意味がない。** 平文で流れるセッションは
トークンと同じだけ漏れる。
